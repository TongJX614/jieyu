# 解语 

> 美妆客服共情副驾 —— 听懂顾客没说出口的那半句
> 「解语」典出「解语花」：解语者，懂人心意之人
> 赛道一 · 数据共情者——消费者的 AI 管家
> 欧莱雅第二届「有意思青年–科技大 Fun 颂」美妆科技黑客松

一个跑在客服坐席旁边的**实时 AI 辅助工作台**。它不替代客服，而是在对话发生的同一秒，把三件事递到客服手边：

1. **读懂** — 融合会员、订单、肤质档案、历史工单四路数据，实时判断消费者的真实意图与情绪走向；
2. **预警** — 识别过敏、舆情外溢、监管投诉、法律追责等风险信号的组合，给出三色分级与处置建议；
3. **给答案** — 一个会**主动弹出来**的话术小助手，顾客每说一句话，它就把 3 条可直接发送的话术递到手边，每条都标出置信度、推荐依据和命中的知识库条款。

## 界面结构


- **最左导航栏**：顶部是当前登录坐席（头像 / 姓名 / 职级 / 在线状态），中间是功能导航（工作台 / **主动关怀雷达** / **多渠道接入** / 风险看板 / 话术库 / **效果评测**），底部是主题切换与设置。看板上挂**待闭环工单数角标**，关怀雷达上挂**高危关怀待触达角标**，渠道上挂**已接入 / 全部渠道数角标**。
- **联系人列表**：每个会话卡显示头像、最后一条消息、时间、**当前风险等级与情绪分**，未读有红点计数；支持关键词搜索与「全部 / 有风险 / 未读」筛选。**点红点先弹未读预览（看原文），再点「打开会话」才进入**，不会一失手就把未读清掉。点一下即**立即接入该客户的历史对话**（不出现「正在接入会话…」的空窗），**每个联系人独立缓存会话**，切走再切回不丢。
- **工具条**：当前客户、三个实时指标、**「实时接入」指示灯**（绿=外部消息通道已连通）、自动演示、重置、模型状态芯片。
- **紧凑数据条（常驻，固定 58px）**：一行给出四个关键读数 —— 迷你情绪曲线 + 本句分 + 情绪词 + 综合指数、Top1 意图与置信度、风险等级 + 风险分 + SLA + 命中信号、**主订单的商品名 / 金额 / 状态 / 商品链接**（商品链接在浮层里另有完整订单号）。右端「全部数据」展开明细。**窗口再窄这条也不会隐藏任何信息**，只按优先级逐级收起（先收曲线、再收意图），并在 ≤820px 让文字变短而不消失。
- **顾客全景浮层（按需展开）**：点「全部数据」后，四张明细卡（逐句情绪走势 / 意图识别 / 多源用户画像 + 关联订单与商品链接 / 风险评估）以**绝对定位浮层**展开在对话区之上。**对话区高度完全不受影响**（实测 787px 恒定），浮层内容超高时内部滚动；`Esc`、右上角「收起」或再点一次「全部数据」都能关掉。展开时话术小助手会自动收起，避免两层浮层互相遮挡。
- **主区下半部分（右栏主体）**：会话流、组合信号预警条、回复输入框（右上角「模拟顾客」可把输入框切成顾客视角）。
- **话术小助手**：可以在屏幕上**任意拖动**，位置记在本机。顾客一发消息它就自动弹出建议；点它可展开 / 收起；双击归位；缩起时用角标提示有几条新建议。气泡顶部有一条**前文体检条**（已读前文 N 句 / 本轮第几句 / 是否依据前文判定），点「查看前文」能直接回看 AI 读到的那几条原话；下面是**本轮已核订单**条（订单号 / 商品 / 金额 / 状态 / 批次 / 退换期 / 物流），每条话术再带 `依据订单 N 项 · 订单接地生成 · 合规通过` 角标 —— **回复必须是「基于订单算出来的」，不是「聊出来的」**。

- **风险预警看板**：指标区给出**待闭环工单数**与**首响达标率**；事件流每行是一个**可展开的工单** —— 闭环状态、责任人、响应时限（走秒）一目了然，点行展开处置详情（处置建议 / 审计轨迹 / 动作按钮 / 责任人 / 处置结论），**处置动作直接在看板完成闭环**；右侧「闭环状态分布」给出五个状态的真实数量与闭环率、首响达标率。

## 一、快速开始

### 方式 A：直接打开（零配置，30 秒）

双击 `index.html` 即可。

浏览器会拦截跨域请求，系统会自动切换到**本地规则引擎**，全部界面、情绪曲线、风险预警、看板和自动演示都能正常跑。适合现场演示兜底。

### 方式 B：本地服务（推荐，真实大模型生效）

```bash
cd beauty-cs-copilot
npm start
```

打开 <http://localhost:5173>，页面上点右上角**「未配置 Key」**按钮，填入 DeepSeek 的 API Key 即可。

服务端会把浏览器的 `/api/chat` 请求转发到上游模型接口，**跨域问题彻底消失**：

- 服务端**没配** `DEEPSEEK_API_KEY` 时 → 透传页面里填写的 Key（Key 仍只存在你自己的浏览器里）；
- 服务端**配了** `DEEPSEEK_API_KEY` 时 → 用服务端 Key，浏览器侧不填也能跑。

接口地址填 `https://api.deepseek.com` 就行，系统会自动补全 `/v1` 与 `/chat/completions`。

### 方式 C：密钥只留在服务端（最安全）

不想把 Key 放进浏览器，就用环境变量：

```bash
# macOS / Linux
export DEEPSEEK_API_KEY=sk-xxxxxxxx
export PORT=5173
npm start
```

```powershell
# Windows PowerShell
$env:DEEPSEEK_API_KEY = "sk-xxxxxxxx"
$env:PORT = "5173"
npm start
```

浏览器侧无需填任何东西，代理会自动注入鉴权头。

## 五、底层架构

这一层是「顾客说的每一句话，AI 都接得住」的保障。

### 5.1 分析管线（harness）：一次分析就是一条显式管线

分析不再是一段散落在 `app.js` 里的 if-else 编排，而是一条**显式、有序、可观测**的管线：

```
顾客消息 ─► AnalysisHarness.run(job)
              │
              ├─ facts        先看清买了什么：装配订单事实包（订单号 / 商品 / 批次 / 成分 / 退换期 / 物流）
              ├─ generate     生成话术：走 provider 降级链 agent → llm → local
              ├─ vision       视觉通道：有图片时做本机像素统计，信号并入同一套风险判定
              ├─ ground       接地校验：没引用订单事实的标记出来，必要时用订单事实兜底
              ├─ compliance   出站合规：逐条检测，标等级 + 给净化文本
              ├─ emotion      逐句情绪：一句一个采样点 + 综合指数 + 走势
              └─ context      前文体检：这一句是在看过多少前文之后判的
```

| 分层 | 文件 | 职责 |
|------|------|------|
| **引擎** | `assets/harness/core.js` | 阶段管线 + 运行轨迹（Trace）+ 生成器注册与降级链。**不认识业务**，只管「按顺序跑、把过程记下来」 |
| **领域阶段** | `assets/harness/stages.js` | 七个阶段的实现，只通过 `state` 传数据，依赖全部注入（因此可在 Node 里用 stub 跑单测） |
| **智能体** | `assets/harness/agent.js` | `generate` 的首选通道：先调工具核实事实，再给结论（详见下文「Agent 通道」） |
| **组装根** | `assets/harness/index.js` | 唯一知道「有哪些模型通道」的地方：注册 `agent` / `llm` / `local`，装配默认管线，导出浏览器单例 |

三条刻意定下的约束：

1. **阶段之间只通过 `state` 传数据**，不共享闭包 —— 顺序与数据依赖一眼可见；
2. **单个阶段抛错默认「跳过不中断」**，保证一条坏数据饿不死整条队列；只有显式标记 `fatal` 的阶段才中止整轮；
3. **换模型 / 加通道只动 `provide()`** —— 阶段与业务代码一行都不用改。

**降级链的语义**（最容易写错的一处）：provider 返回 `null` = **不适用**（静默跳过，**不算降级**）；provider 抛错 = **失败**（记录原因并自动落到下一个）。所以「显式禁用大模型」不会产生虚假的降级告警，而真实失败的原因会原样透出。

默认链是 `agent → llm → local`：**能自主核实的先核实**（agent），退而求其次做一次性推理（llm），最后规则兜底（local）。`agent.js` 未加载时自动退回两级链，管线其余部分不受影响。

**可见可核对**：设置抽屉里的「**分析管线（harness 运行轨迹）**」面板会摊开最近一轮的**阶段耗时 / 决策链 / 结构化判定 / 累计降级次数**。真实一次运行长这样：

```
analysis-8 · 397 ms
facts 0 · provider:llm 266.6 ✗ · provider:local 0.2 · generate 266.5 · ground 0.1 · compliance 0.1 · emotion 0 · context 0
· 先核订单：JD2026092611884 · 紧致抗老精华 30ml（新品首代）→ 装配 15 项事实
· 话术提供者：local（降级原因：HTTP 401 · Authentication Fails）
· 接地校验：3/3 条引用了订单事实
· 出站合规：全部通过
判定：接地 3/3 · 合规 none · 提供者 local · 意图来源 current
```

`core.js`、`stages.js`、`agent.js` 都是 UMD：Node 下直接 `require`，注入 stub 模型通道就能跑真实管线（本项目 harness 单测用的是**真 policy.js / engine.js + stub 模型通道**，44 条断言全绿）。

### 5.2 Agent：先核实事实，再开口

`generate` 的首选通道不是「问模型要答案」，而是一个 **ReAct 工具调用智能体** —— 它自己决定先查什么、再看什么，拿到真实返回后才组织话术：

```
Thought（为什么还要查） → Action（挑一个工具） → Observation（工具真实返回） → 再 Thought … → final
```

工具集全部复用项目已有能力，**不引入新数据源、不新增网络请求**：

| 工具 | 作用 | 数据来源 |
|------|------|---------|
| `list_orders` | 该客户全部订单（避免只看最近一单） | `CRM.allOrdersOf` |
| `get_order` | 凭单号联查批次 / 生产厂 / 关键成分 / 退换期 / 售后政策 | `CRM.byOrderNo` |
| `trace_logistics` | 物流轨迹与履约超时 | `CRM.traceOf` |
| `check_return_window` | 退换期判定 | `CRM.byOrderNo` |
| `search_kb` | 检索既有合规话术与 SOP 条款 | `LocalEngine.REPLY_MAP` |
| `get_risk_policy` | 风险分级标准与处置动作 | `RiskPolicy.LEVELS` |
| `escalate_human` | 生成升级 / 留档处置指令 | `RiskPolicy.LEVELS` |

两条驱动**共用同一套工具、同一条轨迹**：

- **model** — 大模型自主规划（真 ReAct）。复用坐席分析的同一套提示词资产（`LLMClient.SYSTEM_PROMPT` / `buildUserPrompt`），只追加一段「可以先调用工具核实、每步输出一个 JSON」的协议；最多 5 步，收敛后输出与本地引擎同构的 `final`。
- **local** — 规则规划（离线演示 / 模型不可用时）。按本轮消息内容挑工具；**本轮无信号（指代句）时回退到整段前文** —— 与意图识别的「本轮优先 / 无信号回退」是同一套约定。工具仍是真的被执行、轨迹仍是真的产生。

每一步都会写进运行轨迹（`tool:<名字>` 阶段 + 一条决策），设置抽屉里独占一块青色面板：

```
Agent 工具调用 · 规则规划 · 6 步
list_orders → get_order → trace_logistics → search_kb → get_risk_policy → escalate_human
· Agent 调用 凭单号联查订单（get_order）→ 订单号：JD2026092611884（SKU AF-30）…
· Agent 调用 检索话术知识库（search_kb）→ 过敏投诉｜《敏感肌不良反应应对 SOP-2026》第 2 条｜…
判定：接地 3/3 · 合规 none · 提供者 agent · Agent 6 步 · 意图来源 current
```

模型规划中途失败也不会打断整轮：轨迹里记下失败原因，自动切到规则规划（同一套工具），**Agent 这一环永远有结果**。

### 5.3 所有顾客消息只有一个入口

三条来源全部走 `MessageBus.ingest()`，**不存在第二条旁路**：

```
演示剧本回放 ──┐
坐席模拟顾客 ──┼──► MessageBus.ingest() ──► 订阅者 ──► 串行分析队列 ──► 本地引擎 / 大模型
外部系统推送 ──┘        （幂等 · 序号 · 审计）              （严格按到达顺序，逐条分析）
```

| 机制 | 解决的问题 |
|------|-----------|
| **幂等**（按 `msgId` 去重） | 外部系统重推、SSE 断线重连补拉，都不会重复触发分析 |
| **单调序号** `seq` | 每条消息带递增序号，`gaps()` 可直接检测出「序号空洞」即漏收 |
| **审计日志** | 环形缓冲 + localStorage 落盘，刷新页面不丢；看板实时显示「已接收 / 未分析」 |
| **分析确认** `ack(id)` | 分析完成才确认。未确认数量即「已收到但尚未分析」，可核对 AI 是否漏掉任何一句 |
| **串行队列** | 分析任务严格排队执行，**杜绝并发导致的「后到的结果覆盖先到的」** |
| **订阅隔离** | 单个订阅者抛错会被捕获计数，不影响其他订阅者与后续消息 |
| **会话隔离** | 每个联系人独立维护会话、逐句情绪序列与风险记录；切走再切回不丢，非当前会话也能收到并分析消息 |

### 5.4 实时接入通道

外部客服系统向 `POST /api/ingest` 投递消息，所有在线坐席通过 SSE 立刻收到：

```bash
curl -X POST http://localhost:5173/api/ingest \
  -H "Content-Type: application/json" \
  -d '{"msgId":"m-1001","customerId":"allergy","text":"我用完脸红得厉害，想发小红书"}'
```

```json
{ "ok": true, "id": "m-1001", "seq": 1, "customerId": "allergy", "customerName": "周雨桐", "subscribers": 2 }
```

- `customerId` 支持**剧本 key**（`allergy`）、**CRM ID**（`C-100488`）、**客户姓名**三种写法；
- 找不到对应会话时会自动新建一个「外部接入」会话，**消息不会因为查不到客户而丢失**；
- `msgId` 可选，带了就获得幂等保护；`text` 为空返回 400 并计数；
- 浏览器端用 `EventSource` 订阅 `/api/events`，断线自动重连，并用 `?since=<本地游标>` 补拉漏掉的消息；
- 工作台工具条上的**「实时接入」指示灯**变绿即代表通道已连通。

| 接口 | 说明 |
|------|------|
| `POST /api/ingest` | 投递一条顾客消息（幂等，返回序号与在线坐席数） |
| `GET /api/events?since=N` | SSE 实时推送，`hello` 事件回报积压条数并补发漏收消息 |
| `GET /api/messages?since=N` | 补拉接口（非 SSE 环境用） |
| `GET /api/health` | 通道健康度：上游地址、密钥来源、在线坐席数、最新序号 |
| `GET /api/customers` / `GET /api/customers/:id` | 客户档案（支持 CRM ID 或剧本 key） |
| `GET /api/orders/:id` | 订单与商品（含商品链接），返回 `primary` 当前最相关订单 |

### 5.5 订单事实层：先看清对方买了什么，再开口

这是本项目最核心的一条底线：**AI 不是聊天机器人**。顾客说的话到达时，系统必须先装配一份「订单事实包」，回复只能基于这份事实生成 —— 不允许脱离订单泛泛共情。

```
顾客消息到达
  → OrderContext.build()      装配事实包（订单号 / 商品 / SKU / 金额 / 状态 / 批次 /
                              成分 / 退换期 / 物流轨迹 / 超时时长 / 购物车）
  → promptSpec()              事实包 + 「必须引用 ≥2 项订单事实、不得编造」的硬约束，一起注入模型
  → 模型 / 本地引擎生成话术
  → OrderContext.verify()     逐条「接地校验」：没引用任何强事实 → 标记未接地，不进推荐位
  → 全部未接地时 → localReplies() 用事实包直接生成订单接地话术顶到推荐位（永不空手）
```

> 这里的「装配事实包」与「接地校验」就是 [5.1](#51-分析管线harness一次分析就是一条显式管线) 管线上的 `facts` 与 `ground` 两个阶段 —— 领域逻辑集中在 `orderctx.js`，由 harness 按序调用，界面上不用关心它挂在哪一层。

| 机制 | 说明 |
|------|------|
| **意图驱动核对** | `INTENT_FOCUS` 定义每种意图本轮该先核对哪些字段（过敏 → 批次/成分；物流 → 状态/轨迹/超时），核对到的字段在界面上标出 |
| **接地校验** | 强事实 = 订单号 / 商品 / SKU / 批次 / 状态 / 物流 / 轨迹；命中即判定「确实看了订单」 |
| **可见可核对** | 话术小助手顶部一条**本轮已核订单**条：订单号 · 商品 · 金额 · 状态 · 批次 · 退换期 · 物流最新节点；每条话术带 `依据订单 N 项 · 订单接地生成 · 合规通过` 角标 |
| **订单兜底** | 模型不可用或全部未接地时，用 `localReplies()` 按意图生成订单接地话术（引用订单号 / 商品 / 批次 / 金额） |
| **联查明细** | 顾客全景里「关联订单」下方列出**凭订单号联查所得**（批次号 · 生产厂 / 关键成分 / 退换期 / 售后政策 / 购物车）与**物流轨迹**时间线 |

`assets/crm.js` 是浏览器与 Node 共用的同一份数据源（UMD），提供客户档案、订单、SKU、批次成分、物流轨迹与**商品链接**：

- 「主订单」选取规则：优先未签收 / 异常件，其次最近一单 —— 例如过敏案例精准命中那支致敏新品 `AF-30`；
- `byOrderNo()` / `traceOf()` / `allOrdersOf()` 提供凭单号联查；
- 生产环境只需把 `byScenario()` 换成真实 CRM / 订单中心调用，上层无需改动。

| 接口 | 说明 |
|------|------|
| `GET /api/orders/:id` | 该客户订单列表（已合并批次详情），返回 `primary` 当前最相关订单 |
| `GET /api/order/:orderNo` | **凭订单号联查单笔**：订单 + 批次/成分/退换期 + 物流轨迹 + 来源 |

### 5.6 出站合规守卫：AI 给的话，先过一道闸

风险词屏蔽不只在「识别顾客」，还在「约束自己发出去的话」。`assets/guard.js` 对**每一条出站内容**做检测，三级处置：

| 级别 | 处置 | 覆盖 |
|------|------|------|
| **block（禁止发送）** | 输入框锁死发送、话术卡禁用「采用」，必须净化后才能发 | 诱导好评/删帖、引导私下交易、绝对化用语 |
| **rewrite（一键净化）** | 自动把违规词替换为合规表达，一键改写后重校验 | 医疗功效承诺、超权限赔偿 |
| **warn（提示）** | 提示风险但允许发送 | 对抗推责、贬损竞品、效果承诺、隐私外泄、内部信息 |

三处同时生效，源头到出口闭环：

1. **源头** — 禁用语规范注入模型系统提示（`guard.promptSpec()`），从生成端就避免；
2. **坐席可见** — 每条候选话术带 `合规通过` 角标；命中则标红并可「一键净化」；
3. **出口兜底** — 输入框上方的**实时合规条**随输入即时检测，命中 block 直接锁发送。

### 5.7 未读红点与「先看内容再进会话」

联系人卡上的未读标记不是装饰，而是一个**可点的入口**：

- 非当前会话收到消息（无论来自剧本、坐席模拟还是外部推送）都会累积未读原文，红点上显示条数；
- **点红点**先弹一层**未读预览浮层**，列出未读原文与来源标记（剧本 / 外部），再点「打开会话」才真正进入 —— 避免误入会话把未读清掉；
- 未读原文缺缓存时（如剧本初始未读）优雅降级为「打开会话即可查看完整对话」，不假装有内容；
- 打开会话即清空该会话未读与预览浮层。

### 5.8 风险闭环：从「一条状态文案」到「一张可流转的工单」

原来的看板「处置状态」是一句**写死的字符串**（`待专员接管 · 已留档`）——不可流转、没有责任人、没有时限。而赛题产出 2 要求的是**闭环状态跟踪**。现在每条风险事件都会落成一张工单，逻辑在 `assets/casefile.js`。

**五个状态、五条流转，全部显式定义**（虚线不写，看表）：

```
                   ┌── 接管 ──▶ 处理中 ──┬── 升级 ──▶ 已升级
                   │                     │            │
  待处理 ──────────┤                     │            │
                   └── 升级 ─────────────┘            │
                   │                                  │
                   └────────── 标记解决 ─────────────▶ 已解决 ── 归档 ──▶ 已归档
                                                          │                 │
                                                          └── 重新打开 ─────┴──▶ 待处理
```

| 动作 | 允许来源状态 | 约束 |
|------|-------------|------|
| 接管 | 待处理 | 必须落到责任人 |
| 升级 | 待处理 / 处理中 | 必须落到责任人 |
| 标记解决 | 待处理 / 处理中 / 已升级 | **必填处置结论** |
| 归档 | 已解决 | **必填复盘结论** |
| 重新打开 | 已解决 / 已归档 | **必填重开原因** |

**拒绝路径一定给出原因，不静默失败**：在已归档的工单上点「接管」，得到的是「「已归档」不能执行「接管」」；结论留空点「标记解决」，得到「「标记解决」需要填写处置结论」，且状态保持不变。

**响应时限只考核首次响应** —— 这样「15 秒内」才是可考核的硬指标，而不是永远显示同一个字符串：

| 情形 | 显示 |
|------|------|
| 尚未响应，时间充裕 | `限 15 秒内 · 剩 12.4 秒`（每秒走秒，但**只更新时限文本，不重渲染表格**，否则正在输入的结论会失焦） |
| 尚未响应，剩余不足 1/3 | `剩 3.1 秒`（转黄） |
| 尚未响应且已超时 | `已超时 13 小时 40 分`（转红） |
| 已响应且按时 | `达标 · 首响 4.2 秒`（**时钟冻结**，不随后续时间变化） |
| 已响应但超时 | `超时 · 首响 3 分 12 秒` |

等级 / 时限 / 处置建议全部读 `policy.js`（新增的 `slaMs` 是响应时限的数值口径），看板与 AI 判定**同源**。

**历史沉淀事件的迁移**：种子事件里的旧文案（`已升级资深客服`、`自动补偿券已发放`）按语义迁移成真实状态，**原字符串完整保留在审计轨迹里**，迁移可追溯、信息不丢。这类事件没有真实响应时刻，因此**计入达标、但排除在「平均首响」之外** —— 不用 0 秒去伪造一个漂亮的平均值。

**审计轨迹**：创建 / 迁移 / 指派 / 每次流转都写一条（时间 + 动作 + 责任人 + 说明），在工单详情里逐条可查。状态在本机留档，**刷新页面不回退**。

### 5.9 风险等级的统一标准

`assets/policy.js` 的 `RiskPolicy` 是**唯一真源**，本地引擎、大模型提示词、界面看板全部读它。改一个数字，三处同时生效。

| 等级 | 风险分区间 | 响应时限 | 处置动作 |
|------|-----------|---------|---------|
| 高危 | ≥ 58 | 15 秒内 | 立即升级资深客服 · 启动合规留档 · 暂停一切赔偿金额承诺 · 由专员给出确定性方案 |
| 关注 | 28 – 57 | 2 分钟内 | 按标准话术先止损并给出明确时间点 · 记录留档 · 持续观察 |
| 安全 | < 28 | 常规 | 按常规接待流程处理 · 保持响应节奏 · 不做多余承诺 |

**等级由分数唯一判定**，但另有一条**等级下限兜底**规则：部分「权重不大、性质严重」的合规与声誉类信号，一旦命中，等级不得低于其下限。

| 信号 | 权重 | 最低等级 | 为什么 |
|------|------|---------|--------|
| 医疗健康建议边界 | +20 | 关注 | 单说一句「孕妇能用吗」按纯阈值只有 20 分 → 会被判成「安全」，但这是合规红线 |
| 公开平台曝光倾向 | +26 | 关注 | 「我要发小红书」单算只有 26 分，不足阈值，但意味着舆情外溢 |
| 法律追责风险 | +26 | 关注 | 「我要起诉」单算 26 分，涉法场景不能按安全处理 |
| 监管投诉路径 | +30 | 关注 | 防御性下限 |

大模型返回的结果同样会经过 `applyFloors()` 修正，且**不采信模型自己填的 `level` 字段** —— 等级一律由分数 + 下限规则算出，避免模型给出「分数很低但等级很高」这类自相矛盾的结论。

### 5.10 消息接收的可核对性

风险看板的指标区直接暴露总线的真实统计：

- **消息接收 / 未分析** —— 已接收总数 与 尚未确认分析完的条数（正常应恒为 0 或等于队列长度）
- **序号空洞** —— 应为 0；非 0 说明消息真的被丢过
- 设置抽屉里的「实时接入通道」面板还会显示重复拦截数、空消息拦截数、订阅者异常数

### 5.11 多轮上下文：前文在消息到达那一刻就被冻结

AI 不能只看最后一句。指代句（「还是不行」「那怎么办」）本身没有任何关键词，脱离前文根本识别不出诉求。做法：

| 环节 | 实现 |
|---|---|
| **冻结时机** | `snapshotContext()` 在消息**落进会话之前**取快照。若等到分析时才去读会话，排队期间到达的后继消息会被算成「前文」——等于拿后面的话解释前面的一句，分析必然错位 |
| **窗口上限** | 最多带 12 轮进模型（`CTX_TURNS`），保证 `prompt` 不随会话长度无限膨胀；被裁掉的条数会在界面上标出「超窗裁掉 N 条」，不静默丢弃 |
| **本轮优先** | 意图识别先看本轮消息；本轮无信号（落回「常规咨询」）时才回退到整段对话。实测：「还是不行」单独看是「常规咨询」，结合前文后正确判为「过敏投诉」 |
| **可见可核对** | 话术小助手顶部有一条**前文体检条**：已读前文 N 句 / 本轮第几句 / 是否依据前文判定；点「查看前文」可直接回看 AI 读到的每一条原话 |

这条链路对三种来源一视同仁：剧本回放、坐席手动模拟、外部 SSE 推送，都走同一个 `ingest()` → 同一个冻结逻辑。

## 六、AI 推理设计

### 何时调用 AI

**顾客每发一句话就调用一次**，这是本项目唯一的 AI 触发点。触发链路：

```
顾客消息到达 → MessageBus 接收（幂等/序号/审计） → 串行队列排队
    → AnalysisHarness.run(job)   一条显式管线（见 5.1）
         facts 装配订单事实包 → generate 走 agent→llm→local 降级链（Agent 先调工具核实事实，见 5.2）
         → ground 接地校验 → compliance 出站合规 → emotion 逐句情绪 → context 前文体检
    → 产出「本句情绪 + 综合情绪指数 + 意图 + 风险等级 + 3 条候选话术」
    → 更新数据带 / 预警条 / 话术小助手 / 风险看板
```

一次调用同时完成三件事，不需要多次往返：**读懂**（意图 + 情绪）、**预警**（风险等级 + 处置动作）、**给答案**（3 条话术）。管线每一步的耗时与判定都能在设置抽屉里核对。

### 统一 Schema

大模型（`llm.js`）和本地引擎（`engine.js`）输出**完全同构**的 JSON，因此可以无缝互换：

```json
{
  "emotion": {
    "score": 28,
    "index": 41,
    "label": "愤怒",
    "indexLabel": "不满",
    "trend": "down",
    "series": [66, 52, 38, 28]
  },
  "intents": [{ "name": "过敏投诉", "tone": "danger", "confidence": 0.94 }],
  "risk": {
    "level": "high", "score": 100,
    "signals": ["皮肤不良反应", "疑似皮肤损伤", "公开平台曝光倾向", "监管投诉路径"],
    "advice": "命中「皮肤不良反应 + 疑似皮肤损伤 + 公开平台曝光倾向」。立即升级资深客服 · 启动合规留档 · 暂停一切赔偿金额承诺 · 由专员给出确定性方案（响应时限：15 秒内）。"
  },
  "replies": [
    { "text": "…", "confidence": 0.93, "rationale": "…", "kb": "《敏感肌不良反应应对 SOP-2026》" }
  ]
}
```

- `emotion.score` 是**本句**的情绪分（曲线上的一个点），`emotion.series` 是**逐句**序列；
- `emotion.index` 是**综合情绪指数**（对逐句分做 `0.55^n` 衰减加权，反映「此刻这个人整体是什么状态」）；
- `risk.level` 由 `score` 与等级下限共同决定，**不采信模型自填的等级**。

### 三级降级链

```
同源代理 /api/chat  →  浏览器直连官方接口  →  本地规则引擎
```

任何一环失败都会自动落到下一环，并弹出明确提示。**演示不会白屏。**

### 情绪算法：一句一个点

- 曲线按**每一句顾客发言**采样 —— 一条消息里有几句话，就落几个点（按 `。！？；` 断句，长句再按 `，` 切短）。不是「一条消息一个点」；
- 每句独立按情感词典打分（基准 66 分，命中负向词累加扣分）；
- 综合指数再按近端权重 `0.55^n` 做指数衰减加权，让情绪具有**记忆性** —— 顾客说一句「好的」不会把前面的怒气抹掉；
- 走势按「本句 vs 上句」判定，因此能精确反映出**是哪一句让顾客情绪掉下去的**；
- 大模型路径与本地引擎路径共用同一套聚合口径：**逐句序列、综合指数、走势由客户端统一计算**。大模型给出的分数用于覆盖「本轮这一句」的点（保留模型的共情判断），同一消息内的其他分句仍走统一词典口径，曲线不会混尺度。

### 独立的合规兜底

孕产 / 医疗类咨询命中「医疗健康建议边界」信号后会触发等级下限，即使分数不高也不会被当成「安全」。这不是关键词命中，而是**标准里明写的等级规则**。

## 八、这轮新增的五块能力

### 8.1 多模态视觉通道：皮肤照片进同一套风险口径

聊天输入框可附带皮肤照片（「模拟顾客」旁的工具条，或上传本地图片）。图片**不依赖任何云 VLM**：本机 canvas 做像素统计（归一化泛红占比 `(r-g)/r ≥ 0.38` 计为偏红像素），转成结构化观察（无泛红 / 轻度 / 中度 / 明显）后，命中「影像可见皮肤异常」信号，**按 policy.js 里与文本信号同一张权重表**叠加进风险分（+18），等级重算、处置建议同步更新。

分层与 harness 一致：`statsFromPixels` / `observe` 是纯函数（Node 与浏览器同结论），`analyzeFile` / `synth` 只在浏览器可用，并预留 `Vision.register()` 槽位——接真 VLM 时注册即可，风险判定侧一行不改。

### 8.2 主动关怀雷达：出事之前先说话

风险引擎解决「出事之后怎么接住」，关怀雷达（导航栏「关怀」）解决「出事之前能不能先开口」。三路信号全部从既有数据推算，不加埋点：

| 信号 | 推算逻辑 | 示例产出 |
|------|---------|---------|
| ① 复购周期 | 最近一单签收日 + 商品标定用量周期（PIM 兜底表）→ 用量进度 | 安瓶 7 支装超期 43 天 → 高危「复购超期」 |
| ② 权益挽留 | 保级消费线缺口 / 会员周年窗口 / 退换截止倒计时 | 钻石卡年度缺口 ¥4,340 → 高危「保级告急」 |
| ③ 成分冲突 | 肤质档案 × 商品成分（**订单联查优先，PIM 兜底**）+ 成分 × 成分叠加禁忌 | 购物车视黄醇 × 敏感肌 → 高危「加购成分禁忌」 |

每条建议都带数据出处（订单号 / 成分来源 / 口径声明）与可直接发送的话术草稿；有既往过敏史或未闭环工单的客户，销售类建议自动附加「服务优先」提示。导航栏角标实时显示高危关怀条数。基准日可用 `?today=2026-10-14` 固定，演示结论可复现。

### 8.3 会话复盘与交接摘要：接得住，还要传得下去

工作台「复盘」按钮把整个会话折叠成一张交接卡（数据全部来自逐轮判定记录，不重放推理）：

- **来意演进与情绪走势**（`物流催发 → 过敏投诉 · 情绪 57→48 明显转差`）；
- **承诺追踪**——坐席回复里出现「登记 / 跟进 / 补发 / 回电」等承诺词即记一笔，交接时先兑现；
- **未闭环事项**——顾客最后一条未回复、高危事件未接管、话术被合规拦截未补位、影像观察无后续，每条都指向可执行的下一步；
- **纯文本交接摘要**一键复制，直接粘进交接班文档。

### 8.4 隐私合规与审计导出

设置抽屉新增「隐私与审计」：一键把消息审计日志 + 风险事件 + 总线统计导出为 JSON 文件。导出前按**确定性正则**脱敏（手机号 138\*\*\*\*10、邮箱、证件号、订单号 TM2026\*\*\*\*137、客户姓名），图片只记 `hasImage` 布尔值不导出本体；被总线拦截的消息本就不入册。脱敏规则可被测试固定，结果幂等、可复现。

### 8.5 多渠道接入与跨渠道用户合并（导航栏「渠道」）

消费者的声音散在淘宝、天猫、京东、拼多多、抖音、小红书、微信、官网八个地方 —— 只接一个渠道，就只听得见一个渠道的人在说什么。这一块解决三件事：

**① 渠道接入 —— 不是点一下就冒出来，而是一步步跟你要东西。** 八个渠道登记成一份目录，每个渠道声明接入方式（开放平台 API / 插件嵌入 / Webhook 回推）、来源、**能力边界**（能不能拿到消息、订单、物流、售后、会员、内容），以及一份**接入要求**（`SETUP`）：平台侧前置条件、需要申请的凭证字段与格式规则、回调地址约束、OAuth 授权地址与接口权限范围、token 有效期、调用配额、签名方式。接入走**六步向导**：

```
前置条件 → 接入凭证 → 连通性校验 → 店铺授权 → 数据冷启动 → 接入完成
```

- **前置条件**：逐条勾选平台侧要求（企业店铺 / 开发者账号实名 / 应用类目审核 / 权限包获批 / 服务器已备案…），未勾完不放行。
- **接入凭证**：按平台各自的字段填 —— 淘宝 AppKey（8 位）+ AppSecret + 店铺昵称 + 回调地址；京东 AppKey（16 位）；拼多多 client_id（32 位十六进制）；抖店 App Key（19 位）；微信客服需 corpId（`ww` + 16 位）+ Secret + Token（≤32 位）+ EncodingAESKey（**恰好 43 位**）。字段按平台真实规则**本地校验**（位数、字符集、密钥不得与 AppKey 相同），密钥打码显示、不明文回显。
- **回调地址**：强制 HTTPS、公网可达；拒绝 `localhost` / `127.0.0.1` / 内网段，也**拒绝平台自家域名**（淘宝文档明确不许用淘宝/天猫域名做回调）。
- **连通性校验**：不假装成功。演示凭证会**真的探测失败**并回平台真实错误码（`code:15 Invalid app key`），同时指出该去哪个开放平台申请；回调地址不通会回 `HTTP 404` —— 这正是真实接入最常见的卡点，界面会直接告诉你「很多人以为『填完就接上了』，其实平台那边根本没通」。微信客服额外多一步回调 URL 握手（校验 `aesKey`）。
- **店铺授权**：跳转平台 OAuth 地址（如 `oauth.taobao.com/authorize`），把浏览器地址栏里**完整**的回调地址粘回来；没有 `state` 参数直接拒绝（CSRF 校验），`state` 被篡改也拒绝；授权码**一次性**、约 10 分钟过期，重复消费被拦。
- **数据冷启动**：按渠道拉历史会话逐条冷启动，**最后**才写入已接入列表 —— 前面任何一步没过都进不来。

未接入的渠道在目录里单独提示**盲区估算**（按已接入渠道人均消息量外推，明确标注是估算值），卡片上写清「接入要求 N 项前置条件 · M 项凭证字段 · 凭证在 XX 开放平台申请」，点「开始接入 →」进向导。

**② 默认状态是「0 个已接入」—— 不预置任何假的授权。** 打开渠道页看到的是**八个都没接**：目录里八个渠道全为未接入态，`chMeta` 显示「已接入 0 / 8 个渠道 · 累计 0 条跨渠道消息」，合并用户 / 信息断层都是 **0**，跨渠道合并区为空并说明原因。这是刻意的：**没真的接过，就不该显示接过**。要看接入效果时，用页面右上角「载入演示数据」、深链 `?demo=1`、或命令行 `npm run demo:channels`（`--demo`）装载一份**验收用**的接入状态 —— 那是演示，不是默认，且页面顶部会挂一条橙色横幅声明「当前展示的是演示数据」。

> 口径一致性是一条硬约束：**指标与列表必须同进同退**。演示态下「合并用户 4 人」与列表 4 行同时成立；冷启动态下两者同时为 0 —— 不会出现「指标说合并了 4 个人、列表却空着」的自相矛盾。这条在单测（`channels · 统计口径`）和浏览器检查（`channel-wizard`）里都有断言。

**③ token 会过期，过期了消息就断。** token 生命周期做成一等概念：有效期分 `ok` / `soon`（≤3 天，卡片直接给续期入口）/ `expired` / `longterm`（自有渠道无第三方 token）；续期方式按平台区分 `refresh_token`（淘宝 / 京东 / 拼多多 / 抖店 / 小红书）、`gettoken`（微信客服每 2 小时重新获取）、`none`（自有渠道）。演示数据里京东渠道是**故意坏掉的**：宙斯开放平台的 access_token 只有 24 小时且无人续期，于是渠道目录上挂出「授权健康度：1 个已中断」的指标 + 一条红色说明横幅，卡片描红、当日消息归零；它的 `refresh_token` 也已失效，**只能重新走一遍店铺授权**，不能靠点一下续期糊过去。这条链路在演示态下逐项可核对。

**④ 跨渠道用户合并 —— 这是「数据共情者」的地基。** 同一个消费者在不同渠道留下的痕迹，按手机号 / 订单号 / 会员号归并成一个身份，按时间轴排开（演示态下）：

```
周雨桐  139****8802 · JD2026092611884        2 个渠道 · 3 条痕迹 · 1 处断层
  京  09-26 12:08  订单  下单紧致抗老精华 30ml
  红  10-14 22:31  评论  在品牌笔记下留言「我要发小红书」   ← 本渠道看不到
  京  10-14 22:48  售后  反馈泛红并索要说法
```

一个人在天猫问成分、在小红书发空瓶记、回到天猫报不良反应 —— **三块碎片拼起来，AI 才真的懂她在意什么**。`gaps` 字段把「本渠道看不到的其他渠道信息」数出来：信息断层不再是一个抽象概念，而是一个可以指着说的数字（区分**断层**＝渠道已接入却看不到，与**盲区**＝渠道压根没接）。

### 8.7 工作台交互：指示器归属与响应预算

这条改动来自一个真实的界面质疑：**「用户一直显示『准备发送中』，他真的在准备发送吗？」** 查下来是两个独立问题，都改掉了：

- **归属错了**：那个气泡原本挂着**顾客头像**，视觉上读成「顾客正在输入」；实际是**系统在读这条消息**。现在固定渲染为 `.msg.sys` + `AI` 头像 + `AI 解语 · 正在读这条消息…`，谁在干活一目了然。浏览器的 `workbench-indicator` 检查会断言这三件事（挂错侧 / 头像不写 AI / 文案不提 AI 任一条都会失败）。
- **可能卡死**：`analyzeOne` 里 `busy` / `pending` 的复位没有 `try/finally` 保护，管线中途抛错会让「分析中」**永久挂着**、演示循环空转。现在状态复位进了 `finally`，同样一条检查会等到**连续 800ms 干净**才判定收尾，18 秒内不收尾即算卡死失败。

**接口慢怎么办 —— 给交互上预算，而不是让坐席干等。** 三档限制都可在设置抽屉调（`assets/llm.js` 的 `DEFAULTS`）：

| 配置 | 默认 | 作用 |
|---|---|---|
| 单次请求超时 `timeout` | 45s → **20s** | 单次模型调用的上限。队列是串行的，一次卡满 45 秒等于整个工作台停摆 |
| 单轮总预算 `budgetMs` | **15s** | 一轮分析允许花在模型上的总时长（跨 agent 多步 + 自愈重试） |
| 会话调用上限 `maxCalls` | **100 次** | 一个会话内的模型调用总次数，超出即改走本地引擎 |

预算由组装根（`harness/index.js`）在每轮开始时开启、结束时关闭；超时或超配额由 `LLMClient` 抛错 → **降级链自动落到 local**，界面如实提示「已切换本地兜底引擎」并给出原因。核心原则：**宁可给一个规则引擎的结果并说明原因，也不要让坐席盯着空界面干等。** 单次请求的实际等待还会被 `min(timeout, 本轮剩余预算)` 二次夹取，不会出现「单次超时比总预算还长」的荒谬组合。设置抽屉的「模型调用记账」实时显示本会话**已调用次数 / 上限**、超时中断次数与最近一次失败原因 —— 预算是可核对的数字，不是藏在配置里的一句承诺。

### 8.8 全站优化审计：把「哪里慢、哪里废、哪里不合规」变成数字

`npm run audit`（`tools/audit.js`，零依赖，CDP 驱动真实 Chrome）—— 六段**互相独立**的测量，跑完把聚合结论打在终端，明细落 `%TEMP%\cs-audit\report.json`。**跑之前先 `npm start`。** 支持 `--only=perf|a11y|churn|interact|css` 只跑某一段、`--out=DIR` 指定报告目录。

| 维度 | 怎么测 | 结果 |
|---|---|---|
| 可访问性 | 自写对比度检查：解析 `rgb()` → alpha 沿祖先链合成出**真实绘制背景** → WCAG 相对亮度算比值；外加可访问名 / 表单标签 / `img alt` / 标题层级 / 重复 id / 对话框语义 | 12 个「视图 × 主题」组合的**对比度失败 31 → 0**；仅剩 1 条 `info`（4 个 `aria-live` 区域，属预期） |
| 性能 | `Performance.getMetrics`（DOM 节点 / 深度 / layout / styleRecalc / 堆）+ `PerformanceObserver(longtask)` + 视图切换同步耗时 | 各视图 660–911 节点、深 9–11；切换不触发 layout |
| 渲染 churn | `MutationObserver` 统计「一次追加消息到底重建了多少节点」 | 最坏一次替换 **13 → 1** 个节点；疑似全量重建批次 **6 → 0** |
| 拖拽成本 | 180 次 `pointermove` 实测 | 32.3ms（**0.179ms / 次**），布局计算 +1 —— 便宜到不值得引入 rAF 批处理，属于**有数据支撑的「不改」** |
| 定时器 / 监听器泄漏 | 反复切视图 33 轮，每次回到同一视图再计数 | 增长 **0 节点**、堆 **−0.1MB** |
| CSS 死代码 | `CSS.startRuleUsageTracking` 跨全部视图 × 深浅两主题取并集 | 92.1KB 中未命中 **52.1KB（56.5%）** —— 数字如实记录，**未做删除**（56% 里含大量动态类名分支，盲删风险大于收益） |

两个方法论上的坑（都已写进代码注释，避免下次重踩）：

1. **CSS 覆盖率必须在 `reload` 之后取样式表文本。** `Page.reload` 会让样式表拿到**新的 `styleSheetId`**；先取文本再 reload，usage 里的新 id 对不上旧文本，未使用率会恒等于 100%（看起来像「整个样式表都是死代码」）。
2. **浅色主题必须和深色一样被审计。** 默认只有深色，光看默认态会把整套浅色配色漏掉 —— 而实测**浅色才是重灾区**（工作台 43 项 vs 深色 25 项）。为此加了 `?theme=dark|light` 深链供自动化使用。
3. **泄漏探针必须先预热全部视图。** 视图内容是首次进入时才铺的（懒构建）；不预热就取基线，量到的「增长」其实是「还有几屏从没建过」—— 这个假阳性一度报出 +646 节点，预热后真值是 **0**。

**配色为什么要拆 `--accent` 与 `--accent-solid`。** 一个色值不可能同时「够亮到能当文字」和「够暗到能托住白字」。原来 `--accent: #e0715c` 既当文字色、又当实心填充底色（上面压白字），配白字只有 **3.14**，实测不达标。现在拆成两个令牌：`--accent`（文字 / 描边 / 浅底）与 `--accent-solid`（实心填充 + 白字），`--danger` / `--warn` / `--ok` 同理。**31 项不达标没有逐个元素去改，而是收敛到 6 个调色板令牌求解** —— 求解器固定色相与饱和度、只降明度，步进到「在所有真实背景上的最小值 ≥ 4.7」为止（留 0.2 余量，避免四舍五入后卡在 4.49 被判失败）。三级风险徽标也统一成「实心底 + 白字」：中/低档原本用深色文字压亮色底，在浅色主题里同一个 `--warn` 既要当文字（要暗）又要当底（要亮），**无解**。

新增三条浏览器回归护栏 —— 这三类退化肉眼看不见（鼠标用户毫无感觉），只有按键 / 引用断言能守住：

- **`shell-a11y-focus`** —— 三个浮层都要拦 Tab（首尾环绕）、Esc 可关闭、并把焦点**归还给触发按钮**。接入向导此前压根不在 Esc 链里，打开后按 Esc 没反应，键盘用户只能去点右上角那个小叉。向导的每次重绘还会把焦点顶掉，现在按 `data-f` / `data-wz` / `data-ack` 记住焦点「身份」再还原。
- **`workbench-incremental-render`** —— 会话流曾整块 `innerHTML` 重建：每来一条消息就把全部气泡（含 dataURL 图片）重新解析解码一遍。用「**旧节点的引用必须还在**」来守，因为整块重建必然换掉引用；同时断言打字指示器**始终排在最后一条消息之后**。
- **`workbench-scroll-stick`** —— 坐席正在往上翻历史时被硬拽回底部。两条策略都要守：翻历史时不跟随、本就在底部时跟随。

> 这三条探针的**第一版全是假绿 / 假红**，两个坑值得记：① 工作台默认是**坐席回复模式**，直接 `btnSend` 只会追加一条客服消息，得靠剧本自己往下走才间接触发分析 —— 剧本一用尽，断言就静默变成空转（探针必须显式切到「模拟顾客」）。② 测滚动策略时内容只溢出 40px，把 `scrollTop` 拉到 0 距底部也只有 40px，还在 96px 的「贴底」阈值之内，策略判定「跟随」**反而是对的** —— 那测的是阈值边界，不是策略。所以现在要求溢出余量 ≥ 240px。

### 8.9 缺陷排查：七处「不报错、但数字会说谎」的问题

这一轮把已实现的功能逐个模块过了一遍。真正危险的缺陷**不在崩溃里，在「静默失真」里** —— 页面照常跑、测试照常绿，但输出的数字或文字是错的。六处代码 + 一处测试断言，已全部修掉，并钉进 `tests/bugfix.test.js`（18 条断言）：

| # | 位置 | 症状 | 根因 |
|---|---|---|---|
| 1 | `bus.js` `restore()` | 刷新页面后 `report().pendingAck` 虚高 | `ack()` 把确认时间**同时**写进 `acked` 映射与日志条目，但只有日志落盘；`restore()` 只回填了 `log`/`seen`/`seq`，没回填 `acked` → 每条历史消息都被重新算成「已收到、未分析」。**这个字段恰恰是用来证明「没有漏分析」的** |
| 2 | `orderctx.js` `promptSpec()` | 模型提示词里出现「本轮意图为「」相关」 | `(pack.focus ? '' : '')` —— 三元两个分支都是空串，意图名永远渲染成空。意图本可用于 `build()` 里算 `focus`，之后就被丢掉了，没有随事实包传递 |
| 3 | `harness/index.js` `run()` | 重叠运行的两轮分析，第二轮刚设的交互预算被第一轮结束时清 0 | 预算（`LLMClient.deadline`）是**全局单值**，而 `run()` 是异步的。改成挂载深度：进入时只有「0 → 1」那一次设，退出时由**最后一个**离开的人清（不能写成「只有最外层清」—— 最外层可能先于内层结束，那样就没人清了） |
| 4 | `harness/agent.js` `provider()` | 模型规划失败降级后，轨迹里同一件工具出现两次 | `runModel` 和 `runLocal` 共用同一个 `steps` 数组；模型跑到一半抛错时，已执行的模型步骤残留在数组里，规则规划又往里追加 → 「谁真正调了什么」失真 |
| 5 | `assets/harness/stages.js` | 阶段注释出现两个 `④`，文档里还得专门写一条「序号有错位」的注 | 插入 `vision` 阶段时没有顺延后续编号 |
| 6 | `stages.js` / `app.js` / `运行架构说明.md` | `safeText` 被写了两处、文档列为合规阶段产物，**全项目零读取** | 真正的出站闸是 `app.js` 的 `guardOutbound()`（发送那一刻重新 `check()` 并按等级拦截）。一个没人读的字段只会让人误以为「合规阶段已经产出了可直发的文本」→ 直接撤掉 |

修 #2 时还纠了一处**语义**错误：管线里 `build()` 收到的是 `job.priorIntent`（**上一轮**的判定结果，用来决定本轮重点核对哪些事实），本轮意图要等模型/引擎自己判。所以提示词措辞改成「**参考上一轮意图**「X」」而不是原文的「本轮意图」—— 修 bug 时顺手把一个会误导模型的表述也改对了。

第 7 处是**测试自身的缺陷**：`eval.test.js` 的 `fmt()` 只查 `report.rates[name]`，而 `highRecall` 是顶层字段 → 指标一旦掉下来，提示文案会显示「实为 undefined%」。断言本身是对的，但**报错信息会骗人**，真出问题时根本不知道该往哪查。

> 这六处代码缺陷有共同特征：**既有测试一条都没红**（`PASS 434 / FAIL 0` 全程保持）。因为它们不改变函数的返回值轮廓，只让返回值里的某个数字或字符串悄悄失真。所以这次补的断言不是「再测一遍功能」，而是把**错误的形态**钉死 —— 例如 #4 直接用「轨迹里不得出现重复工具名」来守，而不是断言「降级能跑通」。

### 8.10 补齐零覆盖模块：四个业务核心的单测与四处缺陷

上一轮排查留下一个明确缺口：`crm.js`（AI 看到的订单事实的唯一数据源）、`orderctx.js`（接地判定关口）、`casefile.js`（赛题「预警与闭环跟踪」的落地）、`scenarios.js`（演示数据）**四个模块零单测**，一直靠人眼兜底。这一轮补上 `tests/domain.test.js`（99 条断言），并在写测试的过程中又发现四处缺陷：

| # | 位置 | 症状 | 根因 |
|---|---|---|---|
| 1 | `casefile.js` + `app.js` | 责任人栏显示「**抖音商城**」—— 一个渠道被当成了人；且「接管必须指定责任人」的守卫**从不触发** | `recordRisk` 往 `owner` 字段写的是「**推送给谁**」（medium 级直接填渠道名 `c.channel`），闭环模块却把同一个字段当「**谁负责闭环**」。于是 `c.owner` 恒非空 → 守卫永不触发；责任人下拉还把渠道名 `unshift` 进候选并预选中。修法：新增 `ownerAssigned` 区分「通知对象」与「已指派责任人」，只有后者能被沿用 |
| 2 | `casefile.js` `createCase()` | 实时事件若 `status` 文案含「已退款 / 已处理」会被建成 `resolved`，但轨迹首条写的是 `to:'open'`、`respondedAt`/`closedAt` 仍为 0 | `inferState()` 对所有事件都跑。实时事件是这一秒才判出来的，不可能已闭环。内部已自相矛盾：SLA 视图把它当「还没响应」继续倒计时，统计里闭环率算它闭环、响应达标率的分母却不含它 —— 一个工单两套口径。改为只对 `seed` 事件推断 |
| 3 | `crm.js` `allOrdersOf()` | 注释承诺「避免调用方误改真源」，但 `merge()` 是浅拷贝，`trace` / `ingredients` 仍与 `ORDER_DETAILS` **共享引用** | 顶层字段复制了，嵌套数组没复制。新增 `snapshot()` 连数组一并复制，让注释里的承诺成立 |
| 4 | `orderctx.js` `STRONG` | 声明并导出后**全项目零读取** —— 改它对接地判定毫无影响 | `push()` 另外硬编码传布尔值，和 `STRONG` 数组是**两份独立清单**。改为由 `STRONG` 推导，让它成为唯一真源（与 #6 的 `safeText` 同一类：只写不读、看着像真源） |

另外 `scenarios.js` 的注释引用了 `policy.js` 里**并不存在**的 `RISK_SIGNALS / INTENT_POLICY`（实际是 `RiskPolicy.SIGNALS / IntentPolicy.INTENTS`）—— 光靠人眼对不齐，现在 `domain.test.js` 会逐条比对 SEED 数据的信号名 / 意图名 / 等级。

> 新套件断言的是**跨模块契约**，不是「把函数跑一遍」：
> - **数据自洽** —— 剧本库 / CRM 的姓名·等级·肤质·渠道三方对齐；每笔订单都必须有 `ORDER_DETAILS`（缺了批号、成分、退换期，过敏与退换场景的答复会凭空失据）
> - **文档承诺** —— 注释写了「调用方改不到真源」，就断言副本与真源**引用不相等**；「兜底话术一定接地」，就遍历全部 12 个意图逐条验证
> - **状态机** —— 流转被拒必须带原因且不改状态、SLA 时钟在首响后冻结（再等多久文案不变）、`sync` 幂等不打回初始态
>
> #1 有**硬证据**：修复前这一组断言直接红了 9 条（接管守卫形同虚设引发的连锁）。#2 #3 是**潜伏缺陷**（当前 status 文案恰好不触发），断言把它们钉死在「不会再退化」的状态；#4 的断言是**联防**——它锁住「事实标记必须与 STRONG 一致」，防止这个常量再次退化成装饰品。

## 十、常见问题

**Q：点「测试连通性」报「返回内容为空」？**
说明请求已经打通了（HTTP 200），只是没拿到正文。最常见原因是**模型是推理型的**（如 `deepseek-reasoner`、部分 `flash` / thinking 变体），它先输出推理内容、把 token 配额吃光。系统已内置自愈：检测到这种情况会自动**提高 `max_tokens` 并去掉 `response_format` 重试一次**。若仍失败，可把模型名换成 `deepseek-chat`。

**Q：报 `HTTP 400 · Model Not Exist`？**
模型名写错了。DeepSeek 请用 `deepseek-chat`（通用）或 `deepseek-reasoner`（推理）。错误信息现在会**原样透出上游返回的原因**，不会再是含糊的「调用失败」。

**Q：接口地址要带 `/v1` 吗？**
不用纠结。填 `https://api.deepseek.com`、`https://api.deepseek.com/v1`、甚至整条 `.../v1/chat/completions` 都会被自动归一化；直连失败时还会自动换另一种写法重试。

**Q：页面显示「已降级本地引擎」？**
把鼠标悬停在右上角那个状态芯片上，**具体失败原因**会显示出来。常见原因：Key 未填 / 余额不足 / 模型名错误 / 浏览器直连被跨域拦截（改用 `npm start`）。

**Q：能换成其他模型吗？**
可以。设置面板里的接口地址兼容任何 OpenAI 协议端点，例如阿里云百炼、Moonshot、本地 Ollama。支持 `response_format: {"type":"json_object"}` 的模型效果最佳；不支持的模型会自动去掉该参数重试。

**Q：服务端日志显示「未配置」？**
正常。此时浏览器侧填的 Key 会由代理透传；要让服务端代持 Key、浏览器完全不填，设置 `DEEPSEEK_API_KEY` 后重启即可。

**Q：点会话时对话区一直停在「正在接入会话…」？**
已修。根因是点击联系人只切了当前会话下标、没有把该客户的历史接进来，会话是空的所以一直挂着空态。现在点一下会**同步**接入第一条消息（浏览器一次绘制即到位），不再有空窗；真正没有消息的会话会明确写「该会话暂无消息」，不会伪装成正在加载。

**Q：AI 只看最后一句吗？**
不是。每条消息进入总线时都会**冻结一份前文快照**（最多 12 轮）一起送进模型，并且本轮无明确信号时会回退到整段对话去判意图。话术小助手顶部的「已读前文 N 句」和「查看前文」可以直接核对 AI 到底读了什么。
