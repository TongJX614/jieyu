# 解语 Jieyu

> **美妆客服共情副驾** —— 听懂顾客没说出口的那半句
> 「解语」典出「解语花」：解语者，懂人心意之人

| | |
|---|---|
| **赛事** | 欧莱雅第二届「有意思青年 – 科技大 Fun 颂」美妆科技黑客松 |
| **赛道** | 赛道一 · 数据共情者 —— 消费者的 AI 管家 |
| **形态** | 跑在客服坐席旁边的实时 AI 辅助工作台（Web，零构建） |
| **技术** | 原生 HTML / CSS / JS（classic script，无打包器）+ Node 18 原生模块（无运行时依赖） |
| **验证** | 732 条断言 / 14 个套件 · 21 项 CDP 真实浏览器检查 · 20 项架构不变量 |

它**不替代客服**。它在对话发生的同一秒，把三件事递到客服手边：

1. **读懂** —— 融合会员、订单、肤质档案、历史工单四路数据，判断消费者的真实意图与情绪走向；
2. **预警** —— 识别过敏、舆情外溢、监管投诉、法律追责等风险信号的**组合**，给出三色分级、处置动作与响应时限；
3. **给答案** —— 一个会主动弹出来的话术小助手：顾客每说一句话，就把 3 条可直接发送的话术递到手边，每条都标出置信度、推荐依据，以及它引用了订单里的哪几项事实。

## 一、界面布局

坐席一天的动作其实只有三个：**去哪**、**谁在等我**、**现在该说什么**。界面就按这三件事分成三列，任何宽度都不整块隐藏信息、只逐级收起。

| 列 | 宽度 | 里面有什么 |
|---|---|---|
| **导航栏** | 176px | 品牌标志 · 分组导航（接待 / 运营与质检）· 主题切换 · 网站设置 · 当前登录坐席。≤1320px 收成纯图标轨 |
| **会话列** | 296px | 会话卡（摘要 / 时间 / 风险等级 / 情绪分 / 未读红点）+ 搜索与筛选。**只在「坐席工作台」出现**，切到运营视图整体退场 |
| **工作台** | 自适应 | 顶栏 → 数据带 68px → 会话流（气泡 ≤ 640px，右侧常留 128px 给话术小助手）→ 组合信号预警条 → 输入框 |

工作台自上而下的分层，正好是坐席的阅读顺序：

| 层 | 位置 | 回答什么问题 |
|---|---|---|
| 顶栏 | 最上 | 这位是谁、指标如何、要不要开自动演示、模型通不通 |
| 数据带 | 68px 常驻 | 情绪 / 意图 / 风险 / 订单四个读数，右端「全部数据」 |
| 会话流 | 主体 | 现在说到哪儿了；气泡不上拉满宽，长行读起来不丢行 |
| 预警条 | 输入框上方 | 有没有组合信号正在同时成立 |
| 输入框 | 最下 | 这一句该怎么发（含实时合规条） |

点「全部数据」不改变任何列宽：顾客全景以**居中弹窗**展开，压在这三列之上。

### 1.1 导航栏（176px，带字）

顶部是**品牌标志**（解语 / Jieyu），中间是**分组导航**：「接待」组（坐席工作台 / 主动关怀雷达）与「运营与质检」组（多渠道接入 / 风险看板 / 话术库 / 效果评测），底部是主题切换、网站设置与**当前登录坐席**。

- 看板上挂**待闭环工单数**角标，关怀雷达上挂**高危待触达**角标，渠道上挂**已接入 / 全部渠道**角标；
- ≤1320px 收成**纯图标轨**：名字留在 `title` 里，而不是把「坐席工作台」截成「坐..」；
- 品牌标志是**单色掩膜**（图形存在 `assets/img/brand-lockup.png` 的 alpha 通道里，CSS 用 `mask` + `var(--brand-ink)`），深浅两套主题自动换色，窄屏收成独立的 `brand-mark`。

### 1.2 会话列（只在「坐席工作台」出现）

关怀 / 渠道 / 看板 / 话术库 / 评测都是「整页一件事」的运营视图 —— 切过去时会话列整体退场，主区吃满剩余宽度；顶栏也从「当前顾客 + 会话读数」换成**模块身份**（名称 + 一句这页看什么），自动演示与重置随会话上下文一起收起。窄屏抽屉同步退场，遮罩不会盖住这些页面。

每个会话卡显示头像、最后一条消息、时间、**当前风险等级与情绪分**，未读有红点计数，支持关键词搜索与「全部 / 有风险 / 未读」筛选。

- **点红点先弹未读预览**（看原文），再点「打开会话」才进入 —— 不会一失手就把未读清掉；
- 点一下即**立即接入该客户的历史对话**（不出现「正在接入会话…」的空窗）；真正没有消息的会话明确写「该会话暂无消息」，不伪装成加载中；
- **每个联系人独立缓存会话**，切走再切回不丢。

### 1.3 工作台：一条 68px 的数据带

常驻一行给出四个关键读数，右端「全部数据」展开明细：

| 格 | 内容 |
|---|---|
| 情绪 | 迷你曲线 + 本句分 + 情绪词 |
| 意图 | Top1 意图 + 置信度 |
| 风险 | 等级 + 风险分 + SLA + 命中信号 |
| 订单 | 主订单商品名 / 金额 / 状态 / 商品链接（链接只留箭头图标，**商品名优先保住**；完整订单号在浮层里） |

**窗口再窄这条也不隐藏任何信息**，只按优先级逐级收起：≤1440 收曲线 → ≤1180 收意图 → ≤820 让文字变短。

### 1.4 会话流

消息区从顶部起排（会话短时空白落在最后一条与输入框之间 —— 那是「下一条会出现」的位置），气泡最大 `min(76%, 640px)`：坐席话术常常三四行，撑满整宽会拉出 60 字以上的长行，眼睛回行时找不到下一行开头。右侧常留 128px 给话术助手，让它站着的时候不压正文。

**「分析中」指示器属于 AI 侧**：固定渲染成 `.msg.sys` + `AI` 头像 + 「AI 解语 · 正在读这条消息…」。挂顾客头像会被读成「顾客正在输入」——它是系统在读，不是顾客在打字。

### 1.5 顾客全景弹窗（按需展开）

点「全部数据」打开一屏居中弹窗（带遮罩），三段排布：

1. **此刻的判断** —— 逐句情绪曲线 / 意图与「判的是哪句话」的原话 / 风险等级 + 分值 + 建议；
2. **这个人是谁、买了什么** —— 多源画像 8 项按行排 / 关联订单 + 凭据联查 + 物流轨迹；
3. **主动关怀索引** —— 几条待触达 + 一键进关怀雷达。

栅格随视口在 3 / 2 / 1 列之间切换，高度跟随视口（`100dvh - 56px`），内容再长也只在弹窗内部滚动，**不会把某张卡截掉半张**。`Esc`、点遮罩、右上角关闭或再点一次「全部数据」都能关掉；打开时焦点进入弹窗并在内部循环（Tab 首尾环绕），关闭后归还给触发按钮，切到别的视图自动收起。展开时话术小助手自动收起 —— 两层浮层不互相遮挡。

### 1.6 话术小助手与桌宠

小助手可以在屏幕上**任意拖动**，位置记在本机。顾客一发消息就自动弹出；点它展开 / 收起，双击归位，缩起时用角标提示有几条新建议。

气泡里三块信息，全部用来**核对 AI 到底看了什么**：

- **前文体检条** —— 已读前文 N 句 / 本轮第几句 / 是否依据前文判定，点「查看前文」直接回看 AI 读到的那几条原话；
- **本轮已核订单** —— 订单号 · 商品 · 金额 · 状态 · 批次 · 退换期 · 物流最新节点；
- 每条话术带 `依据订单 3 项 · 订单接地生成 · 合规通过` 角标 —— **回复必须是基于订单算出来的，不是聊出来的**。

**桌宠手上那件**：它会判断这通会话在聊哪一类商品，把对应道具拿在手里（口红 / 眼影盘 / 睫毛膏 / 精华 / 粉饼 / 香水 / 护手霜）。判定顺序是「本会话最近一句提到的商品」优先、「订单」兜底 —— 一句「帮我退款」不会让它随手抓一件。词表与道具映射只在 `propfit.js` 一处；真数据接商品中心时，订单带 `category` 就按 PIM 类目直查。气泡顶部那行「手上这件 · 口红 · 顾客这句话里提到」就是这次判定的出处。

**它自己也有生活**：没人搭理它时，每隔 9–20 秒点头 / 挥手 / 原地跳 / 转个圈。拿着东西时**照样做** —— 三个动作各渲了一套持物版，招手换到右手（左臂拿着东西抬不起来），转圈时道具跟着身体绕一圈。唯一没有持物版的是「跳」，那一下改成纯 2D 的「轻轻一沉」。用户一交互就重新计时，绝不在拖动中途突然换动作。

**帧率是看得见的**：fps = 帧数 / 循环时长，两个都要调对。待机 28 格 / 5.2s、跑步 24 格 / 0.87s（≈27fps）、持物呼吸 20 格 / 4.2s、持物点头 20 格 / 1.05s、持物挥手与转圈各 28 格。`steps(N)` 必须等于序列帧格子数 —— 写大了会在格子尽头露出半个人，写小了动作整体变慢。

### 1.7 六个运营视图

| 视图 | 一句话 |
|---|---|
| **主动关怀雷达** | 左索引 + 右详情：左列按姓名排列（卡上带「高危 3 / 关注 2」计数），顶部标签「全部 5 / 高危 4 / 关注 3 / 提示 1」（数字是**几位客户**），右列只渲染选中客户的条目 |
| **多渠道接入** | 八渠道目录 + 六步接入向导 + token 健康度 + 跨渠道用户合并，**默认 0 个已接入** |
| **风险看板** | 指标区（待闭环数 / 首响达标率）+ 事件流独占一行（每行可展开成工单，就地闭环）+ 一行四张分布卡 |
| **话术库** | 全文检索 + 自建条目（可删），工作台每条建议都能「存入库」 |
| **效果评测** | 先给结论（全部通过 / N 条判错），四项指标每个数字下面直接写「14 条里 14 条认对」，明细收进折叠区 |
| **账号中心** | 工号 + 口令登录、坐席名单、在线状态切换、当前坐席统计 |

**风险看板为什么不画进度条**：分布卡原本是「名称 + 进度横条 + 数字」，一张卡被横条撑到近两倍高，挤得下面的分级标准要滚动。改成只留「名称 + 命中次数」（`.srow`，数字右对齐）+ 分级标准压成三行之后，**1440×900 下整页零滚动**。

### 1.8 设置分两处，各管一件事

| 入口 | 面板 | 管什么 |
|---|---|---|
| 右上角模型状态药丸 | `#engineRoot` | 模型与推理：接口地址、Key、模型名、超时 / 预算 / 调用上限、分析管线轨迹、Agent 工具调用轨迹、模型调用记账 |
| 侧栏齿轮 | `#drawerRoot` | 网站设置：外观、起始页、桌宠、自动弹话术、SLA 走秒、风险提示、隐私与审计导出、账号入口、关于 |

身份卡是按钮，点开账号面板。**提醒与记录是两件事**：关掉「风险提示」只关打扰，风险事件照常入册。

## 二、快速开始

### 方式 A：直接打开（零配置，30 秒）

双击 `index.html` 即可。浏览器会拦截跨域请求，系统自动切到**本地规则引擎** —— 全部界面、情绪曲线、风险预警、看板和自动演示都能正常跑。适合现场演示兜底。

### 方式 B：本地服务（推荐，真实大模型生效）

```bash
cd beauty-cs-copilot
npm start
```

打开 <http://localhost:5173>，点右上角**「未配置 Key」**，填入 DeepSeek 的 API Key。服务端把 `/api/chat` 转发到上游，**跨域问题彻底消失**：

- 服务端**没配** `DEEPSEEK_API_KEY` → 透传页面里填的 Key（Key 仍只存在你自己的浏览器）；
- 服务端**配了** `DEEPSEEK_API_KEY` → 用服务端 Key，浏览器侧不填也能跑。

接口地址填 `https://api.deepseek.com` 就行，系统会自动补全 `/v1` 与 `/chat/completions`。

演示账号：工号 `CS013` / 口令 `1234`（口令写在文档与启动横幅里 —— 就不假装它是安全的；账号存 `sha256(salt:pin)`）。

### 方式 C：密钥只留在服务端（最安全）

```bash
# macOS / Linux
export DEEPSEEK_API_KEY=sk-xxxxxxxx
export PORT=5173
npm start
```

```powershell
# Windows PowerShell
$env:DEEPSEEK_API_KEY = "sk-xxxxxxxx"
$env:PORT = "5173"
npm start
```

浏览器侧无需填任何东西，代理会自动注入鉴权头。

### 密钥安全

| 做法 | 说明 |
|---|---|
| 源码零硬编码 | 代码中不存在任何 API Key 字面量（`ST06` 静态检查守着） |
| 浏览器侧只存 localStorage | 页面里填的 Key 存在本机，不随文件分发 |
| 服务端可代持 | 用 `DEEPSEEK_API_KEY` 环境变量时，Key 从不进入浏览器 |
| `.gitignore` 已就位 | 屏蔽 `.env`、`*.key`、`secrets.json`、`server/data/` |
| 支持随时清除 | 网站设置提供「清除本机数据」 |

推送前自查：`grep -rn "sk-" . --exclude-dir=node_modules`

## 五、架构是怎样跑起来的

### 5.1 分析管线（harness）

分析不是散落在 `app.js` 里的 if-else，而是一条**显式、有序、可观测**的管线：

```
顾客消息 ─► MessageBus.ingest()（幂等 / 序号 / 审计）
         ─► 串行队列（严格按到达顺序，逐条分析）
         ─► AnalysisHarness.run(job)
              │
              ├─ ① facts        先看清买了什么：装配订单事实包（单号 / 商品 / 批次 / 成分 / 退换期 / 物流）
              ├─ ② generate     生成话术：走降级链 agent → llm → local
              ├─ ③ vision       视觉通道：有图片时做本机像素统计，信号并入同一套风险判定
              ├─ ④ ground       接地校验：没引用订单事实的标出来，必要时用订单事实兜底
              ├─ ⑤ compliance   出站合规：逐条检测，标等级 + 给净化文本
              ├─ ⑥ emotion      逐句情绪：一句一个采样点 + 综合指数 + 走势
              └─ ⑦ context      前文体检：这一句是在看过多少前文之后判的
```

| 分层 | 文件 | 职责 |
|------|------|------|
| **引擎** | `harness/core.js` | 阶段管线 + 运行轨迹 + 生成器注册与降级链。**不认识业务**，只管「按顺序跑、把过程记下来」 |
| **领域阶段** | `harness/stages.js` | 七个阶段的实现，只通过 `state` 传数据、依赖全部注入（因此可在 Node 里用 stub 跑单测） |
| **智能体** | `harness/agent.js` | `generate` 的首选通道：先调工具核实事实，再给结论 |
| **组装根** | `harness/index.js` | 唯一知道「有哪些模型通道」的地方：注册 `agent` / `llm` / `local` |

三条刻意定下的约束：

1. **阶段之间只通过 `state` 传数据**，不共享闭包 —— 顺序与数据依赖一眼可见；
2. **单个阶段抛错默认「跳过不中断」**，保证一条坏数据饿不死整条队列；只有显式 `fatal` 才中止整轮；
3. **换模型 / 加通道只动 `provide()`** —— 阶段与业务代码一行都不用改。

**降级链的语义**（最容易写错的一处）：provider 返回 `null` = **不适用**（静默跳过，**不算降级**）；provider 抛错 = **失败**（记录原因并自动落到下一个）。所以「显式禁用大模型」不会产生虚假的降级告警，而真实失败的原因会原样透出。

**可见可核对**：设置抽屉的「分析管线（harness 运行轨迹）」面板会摊开最近一轮的阶段耗时 / 决策链 / 结构化判定 / 累计降级次数。真实一次运行长这样：

```
analysis-8 · 397 ms
facts 0 · provider:llm 266.6 ✗ · provider:local 0.2 · generate 266.5 · ground 0.1 · compliance 0.1 · emotion 0 · context 0
· 先核订单：JD2026092611884 · 紧致抗老精华 30ml（新品首代）→ 装配 15 项事实
· 话术提供者：local（降级原因：HTTP 401 · Authentication Fails）
· 接地校验：3/3 条引用了订单事实
· 出站合规：全部通过
判定：接地 3/3 · 合规 none · 提供者 local · 意图来源 current
```

`core.js` / `stages.js` / `agent.js` 都是 UMD：Node 下直接 `require`，注入 stub 模型通道就能跑真实管线（harness 单测用的是**真 policy.js / engine.js + stub 模型通道**）。

### 5.2 Agent：先核实事实，再开口

`generate` 的首选通道不是「问模型要答案」，而是一个 **ReAct 工具调用智能体** —— 它自己决定先查什么、再看什么，拿到真实返回后才组织话术：

```
Thought（为什么还要查） → Action（挑一个工具） → Observation（工具真实返回） → 再 Thought … → final
```

工具集全部复用项目已有能力，**不引入新数据源、不新增网络请求**：

| 工具 | 作用 | 数据来源 |
|------|------|---------|
| `list_orders` | 该客户全部订单（避免只看最近一单） | `CRM.allOrdersOf` |
| `get_order` | 凭单号联查批次 / 生产厂 / 成分 / 退换期 / 售后政策 | `CRM.byOrderNo` |
| `trace_logistics` | 物流轨迹与履约超时 | `CRM.traceOf` |
| `check_return_window` | 退换期判定 | `CRM.byOrderNo` |
| `search_kb` | 检索既有合规话术与 SOP 条款 | `LocalEngine.REPLY_MAP` |
| `get_risk_policy` | 风险分级标准与处置动作 | `RiskPolicy.LEVELS` |
| `escalate_human` | 生成升级 / 留档处置指令 | `RiskPolicy.LEVELS` |

两条驱动**共用同一套工具、同一条轨迹**：

- **model** —— 大模型自主规划（真 ReAct）。复用坐席分析的同一套提示词资产（`SYSTEM_PROMPT` / `buildUserPrompt`），只追加「可以先调工具核实、每步输出一个 JSON」的协议；最多 5 步，收敛后输出与本地引擎同构的 `final`；
- **local** —— 规则规划（离线演示 / 模型不可用）。按本轮消息挑工具；**本轮无信号（指代句）时回退到整段前文** —— 与意图识别的「本轮优先 / 无信号回退」是同一套约定。工具仍真的被执行、轨迹仍真的产生。

模型规划中途失败不会打断整轮：轨迹里记下失败原因，自动切到规则规划（同一套工具），**Agent 这一环永远有结果**。界面如实标注这一轮是 `model` 还是 `local`，不把规则规划说成模型规划。

### 5.3 所有顾客消息只有一个入口

三条来源全部走 `MessageBus.ingest()`，**不存在第二条旁路**：

```
演示剧本回放 ──┐
坐席模拟顾客 ──┼──► MessageBus.ingest() ──► 订阅者 ──► 串行分析队列 ──► 本地引擎 / 大模型
外部系统推送 ──┘        （幂等 · 序号 · 审计）              （严格按到达顺序，逐条分析）
```

| 机制 | 解决的问题 |
|------|-----------|
| **幂等**（按 `msgId` 去重） | 外部系统重推、SSE 断线重连补拉，都不会重复触发分析 |
| **单调序号** `seq` | 每条消息带递增序号，`gaps()` 直接检测「序号空洞」即漏收 |
| **审计日志** | 环形缓冲 + localStorage 落盘，刷新不丢；看板实时显示「已接收 / 未分析」 |
| **分析确认** `ack(id)` | 分析完成才确认。未确认数量即「已收到但尚未分析」，可核对 AI 是否漏掉任何一句 |
| **串行队列** | 分析任务严格排队，杜绝并发导致的「后到的结果覆盖先到的」 |
| **订阅隔离** | 单个订阅者抛错会被捕获计数，不影响其他订阅者与后续消息 |
| **会话隔离** | 每个联系人独立维护会话、逐句情绪序列与风险记录；非当前会话也能收到并分析消息 |

### 5.4 订单事实层：先看清对方买了什么，再开口

这是本项目最核心的一条底线：**AI 不是聊天机器人**。回复只能基于订单事实生成，不允许脱离订单泛泛共情。

```
顾客消息到达
  → OrderContext.build()      装配事实包（单号 / 商品 / SKU / 金额 / 状态 / 批次 /
                              成分 / 退换期 / 物流轨迹 / 超时时长 / 购物车）
  → promptSpec()              事实包 + 「必须引用 ≥2 项订单事实、不得编造」的硬约束，一起注入模型
  → 模型 / 本地引擎生成话术
  → OrderContext.verify()     逐条接地校验：没引用任何强事实 → 标记未接地，不进推荐位
  → 全部未接地时 → localReplies() 用事实包直接生成订单接地话术顶到推荐位（永不空手）
```

> 这里的「装配事实包」与「接地校验」就是管线上的 `facts` 与 `ground` 两个阶段 —— 领域逻辑集中在 `orderctx.js`，由 harness 按序调用。

| 机制 | 说明 |
|------|------|
| **意图驱动核对** | `INTENT_FOCUS` 定义每种意图本轮该先核对哪些字段（过敏 → 批次/成分；物流 → 状态/轨迹/超时），核对到的字段在界面上标出 |
| **接地校验** | 强事实 = 订单号 / 商品 / SKU / 批次 / 状态 / 物流 / 轨迹；命中即判定「确实看了订单」 |
| **可见可核对** | 话术小助手顶部的「本轮已核订单」条 + 每条话术的 `依据订单 N 项` 角标 |
| **订单兜底** | 模型不可用或全部未接地时，按意图生成订单接地话术（引用单号 / 商品 / 批次 / 金额） |
| **联查明细** | 顾客全景里「关联订单」下方列出凭单号联查所得（批次 · 生产厂 / 成分 / 退换期 / 售后政策 / 购物车）与物流时间线 |

`assets/crm.js` 是浏览器与 Node 共用的同一份数据源（UMD）。「主订单」选取规则：优先未签收 / 异常件，其次最近一单 —— 过敏案例精准命中那支致敏新品 `AF-30`。生产环境只需把 `byScenario()` 换成真实 CRM / 订单中心调用，上层无需改动。

### 5.5 出站合规守卫：AI 给的话，先过一道闸

风险词屏蔽不只在「识别顾客」，还在「约束自己发出去的话」。`guard.js` 对每条出站内容做检测，三级处置：

| 级别 | 处置 | 覆盖 |
|------|------|------|
| **block（禁止发送）** | 输入框锁死发送、话术卡禁用「采用」，必须净化后才能发 | 诱导好评 / 删帖、引导私下交易、绝对化用语 |
| **rewrite（一键净化）** | 自动把违规词替换为合规表达，一键改写后重校验 | 医疗功效承诺、超权限赔偿 |
| **warn（提示）** | 提示风险但允许发送 | 对抗推责、贬损竞品、效果承诺、隐私外泄、内部信息 |

三处同时生效，源头到出口闭环：**源头**（禁用语注入模型系统提示 `guard.promptSpec()`）→ **坐席可见**（每条候选话术带「合规通过」角标，命中标红并可一键净化）→ **出口兜底**（输入框上方的实时合规条随输入即时检测，命中 block 直接锁发送）。

### 5.6 风险闭环：从一句写死的状态文案，到一张可流转的工单

原来的看板「处置状态」是一句写死的字符串（`待专员接管 · 已留档`）—— 不可流转、没有责任人、没有时限。现在每条风险事件都会落成一张工单，逻辑在 `casefile.js`。**五个状态、五条流转，全部显式定义**：

| 动作 | 从 | 到 | 必填 | 为什么 |
|---|---|---|---|---|
| 接管 | 待处理 | 处理中 | 责任人 | 「谁在管」必须是人，不能是渠道名 |
| 升级 | 待处理 / 处理中 | 已升级 | 责任人 | 升级不是状态装饰，得有人接手 |
| 标记解决 | 待处理 / 处理中 / 已升级 | 已解决 | **处置结论** | 结案必须留下「怎么解决的」 |
| 归档 | 已解决 | 已归档 | **复盘结论** | 归档是沉淀，不是关掉 |
| 重新打开 | 已解决 / 已归档 | 待处理 | **重开原因** | 允许反悔，但要说明为什么 |

主线只有一条：**待处理 → 处理中 → 已升级 → 已解决 → 已归档**；`升级` 可以从待处理直接跳，`重新打开` 则把已解决 / 已归档拉回待处理。这张表就是唯一口径，界面上的按钮可用状态直接由它推导 —— 不是各写一套 if。

**拒绝路径一定给出原因，不静默失败**：在已归档的工单上点「接管」得到「「已归档」不能执行「接管」」；结论留空点「标记解决」得到「「标记解决」需要填写处置结论」，状态保持不变。

**响应时限只考核首次响应** —— 这样「15 秒内」才是可考核的硬指标，而不是永远显示同一个字符串：

| 情形 | 显示 |
|------|------|
| 尚未响应，时间充裕 | `限 15 秒内 · 剩 12.4 秒`（每秒走秒，但**只更新时限文本不重渲染表格**，否则正在输入的结论会失焦） |
| 尚未响应，剩余不足 1/3 | `剩 3.1 秒`（转黄） |
| 尚未响应且已超时 | `已超时 13 小时 40 分`（转红） |
| 已响应且按时 | `达标 · 首响 4.2 秒`（**时钟冻结**，不随后续时间变化） |
| 已响应但超时 | `超时 · 首响 3 分 12 秒` |

等级 / 时限 / 处置建议全部读 `policy.js`（`LEVELS[].slaMs` 是响应时限的数值口径），看板与 AI 判定**同源**。

**历史沉淀事件的迁移**：种子事件里的旧文案（`已升级资深客服`、`自动补偿券已发放`）按语义迁移成真实状态，**原字符串完整保留在审计轨迹里**。这类事件没有真实响应时刻，因此**计入达标、但排除在「平均首响」之外** —— 不用 0 秒去伪造一个漂亮的平均值。

**审计轨迹**：创建 / 迁移 / 指派 / 每次流转都写一条（时间 + 动作 + 责任人 + 说明），在工单详情里逐条可查，**刷新页面不回退**。

### 5.7 风险等级的统一标准

`policy.js` 的 `RiskPolicy` 是**唯一真源**，本地引擎、大模型提示词、界面看板全部读它。改一个数字，三处同时生效。

| 等级 | 风险分区间 | 响应时限 | 处置动作 |
|------|-----------|---------|---------|
| 高危 | ≥ 58 | 15 秒内 | 立即升级资深客服 · 启动合规留档 · 暂停一切赔偿金额承诺 · 由专员给出确定性方案 |
| 关注 | 28 – 57 | 2 分钟内 | 按标准话术先止损并给出明确时间点 · 记录留档 · 持续观察 |
| 安全 | < 28 | 常规 | 按常规接待流程处理 · 保持响应节奏 · 不做多余承诺 |

**等级由分数唯一判定**，但另有一条**等级下限兜底**：部分「权重不大、性质严重」的合规与声誉类信号，一旦命中，等级不得低于其下限。

| 信号 | 权重 | 最低等级 | 为什么 |
|------|------|---------|--------|
| 医疗健康建议边界 | +20 | 关注 | 单说一句「孕妇能用吗」按纯阈值只有 20 分 → 会被判成「安全」，但这是合规红线 |
| 公开平台曝光倾向 | +26 | 关注 | 「我要发小红书」单算只有 26 分，不足阈值，但意味着舆情外溢 |
| 法律追责风险 | +26 | 关注 | 「我要起诉」单算 26 分，涉法场景不能按安全处理 |
| 监管投诉路径 | +30 | 关注 | 防御性下限 |

全库共 **13 个风险信号**、**11 个意图**（另有 `default` 兜底话术键），全部登记在 `policy.js`。大模型返回的结果同样经过 `applyFloors()` 修正，且**不采信模型自己填的 `level` 字段** —— 等级一律由分数 + 下限规则算出。

### 5.8 多轮上下文：前文在消息到达那一刻就被冻结

AI 不能只看最后一句。指代句（「还是不行」「那怎么办」）本身没有任何关键词，脱离前文根本识别不出诉求。

| 环节 | 实现 |
|---|---|
| **冻结时机** | `snapshotContext()` 在消息**落进会话之前**取快照。若等到分析时才读会话，排队期间到达的后继消息会被算成「前文」—— 等于拿后面的话解释前面的一句，分析必然错位 |
| **窗口上限** | 最多带 12 轮进模型（`CTX_TURNS`）；被裁掉的条数会在界面标出「超窗裁掉 N 条」，不静默丢弃 |
| **本轮优先** | 意图识别先看本轮；本轮无信号（落回常规咨询）时才回退到整段对话。实测「还是不行」单独看是常规咨询，结合前文后正确判为过敏投诉 |
| **可见可核对** | 话术小助手顶部「已读前文 N 句 / 本轮第几句 / 是否依据前文判定」，点「查看前文」回看 AI 读到的每一条原话 |

这条链路对三种来源一视同仁：剧本回放、坐席手动模拟、外部 SSE 推送，都走同一个 `ingest()` → 同一个冻结逻辑。

### 5.9 实时接入通道

外部客服系统向 `POST /api/ingest` 投递消息，所有在线坐席通过 SSE 立刻收到：

```bash
curl -X POST http://localhost:5173/api/ingest \
  -H "Content-Type: application/json" \
  -d '{"msgId":"m-1001","customerId":"allergy","text":"我用完脸红得厉害，想发小红书"}'
```

```json
{ "ok": true, "id": "m-1001", "seq": 1, "customerId": "allergy", "customerName": "周雨桐", "subscribers": 2 }
```

- `customerId` 支持**剧本 key**（`allergy`）、**CRM ID**（`C-100488`）、**客户姓名**三种写法；
- 找不到对应会话时自动新建「外部接入」会话，**消息不会因为查不到客户而丢失**；
- `msgId` 可选，带了就获得幂等保护；`text` 为空返回 400 并计数；
- 浏览器端用 `EventSource` 订阅 `/api/events`，断线自动重连，并用 `?since=<本地游标>` 补拉漏掉的消息；
- 工具条上的「实时接入」指示灯变绿即代表通道已连通。

## 六、AI 推理设计

### 何时调用 AI

**顾客每发一句话就调用一次**，这是本项目唯一的 AI 触发点：

```
顾客消息到达 → MessageBus 接收（幂等/序号/审计） → 串行队列排队
    → AnalysisHarness.run(job)  facts → generate → vision → ground → compliance → emotion → context
    → 产出「本句情绪 + 综合情绪指数 + 意图 + 风险等级 + 3 条候选话术」
    → 更新数据带 / 预警条 / 话术小助手 / 风险看板
```

一次调用同时完成三件事：**读懂**（意图 + 情绪）、**预警**（风险等级 + 处置动作）、**给答案**（3 条话术）。每一步的耗时与判定都能在设置抽屉里核对。

### 统一 Schema

大模型（`llm.js`）和本地引擎（`engine.js`）输出**完全同构**的 JSON，因此可以无缝互换：

```json
{
  "emotion": {
    "score": 28,
    "index": 41,
    "label": "愤怒",
    "indexLabel": "不满",
    "trend": "down",
    "series": [66, 52, 38, 28]
  },
  "intents": [{ "name": "过敏投诉", "tone": "danger", "confidence": 0.94 }],
  "risk": {
    "level": "high", "score": 100,
    "signals": ["皮肤不良反应", "疑似皮肤损伤", "公开平台曝光倾向", "监管投诉路径"],
    "advice": "命中「皮肤不良反应 + 疑似皮肤损伤 + 公开平台曝光倾向」。立即升级资深客服 · 启动合规留档 · 暂停一切赔偿金额承诺 · 由专员给出确定性方案（响应时限：15 秒内）。"
  },
  "replies": [
    { "text": "…", "confidence": 0.93, "rationale": "…", "kb": "《敏感肌不良反应应对 SOP-2026》" }
  ]
}
```

- `emotion.score` 是**本句**的情绪分，`emotion.series` 是**逐句**序列，`emotion.index` 是**综合指数**（对逐句分做 `0.55^n` 衰减加权）；
- `risk.level` 由 `score` 与等级下限共同决定，**不采信模型自填的等级**。

### 情绪算法：一句一个点

- 曲线按**每一句顾客发言**采样 —— 一条消息里有几句话就落几个点（按 `。！？；` 断句，长句再按 `，` 切短）。不是「一条消息一个点」；
- 每句独立按情感词典打分（基准 66 分，命中负向词累加扣分）；
- 综合指数按近端权重 `0.55^n` 指数衰减加权，让情绪具有**记忆性** —— 顾客说一句「好的」不会把前面的怒气抹掉；
- 走势按「本句 vs 上句」判定，因此能精确反映出**是哪一句让顾客情绪掉下去的**；
- 大模型路径与本地引擎共用同一套聚合口径：逐句序列、综合指数、走势由客户端统一计算。模型给出的分数只覆盖「本轮这一句」，同一消息内的其他分句仍走统一词典口径，曲线不会混尺度。

### 三级降级链与交互预算

```
同源代理 /api/chat  →  浏览器直连官方接口  →  本地规则引擎
```

任何一环失败都会自动落到下一环，并弹出明确提示。**演示不会白屏。**

接口慢怎么办 —— 给交互上预算，而不是让坐席干等（三档都可在设置抽屉调，`llm.js` 的 `DEFAULTS`）：

| 配置 | 默认 | 作用 |
|---|---|---|
| 单次请求超时 `timeout` | 45s → **20s** | 单次模型调用的上限。队列是串行的，一次卡满 45 秒等于整个工作台停摆 |
| 单轮总预算 `budgetMs` | **15s** | 一轮分析允许花在模型上的总时长（跨 agent 多步 + 自愈重试） |
| 会话调用上限 `maxCalls` | **100 次** | 一个会话内的模型调用总次数，超出即改走本地引擎 |

预算由组装根在每轮开始时开启、结束时关闭；超时或超配额由 `LLMClient` 抛错 → **降级链自动落到 local**，界面如实提示「已切换本地兜底引擎」并给出原因。单次等待还会被 `min(timeout, 本轮剩余预算)` 二次夹取，不会出现「单次超时比总预算还长」的组合。核心原则：**宁可给一个规则引擎的结果并说明原因，也不要让坐席盯着空界面干等。**

## 八、功能地图

### 8.1 视觉通道：皮肤照片进同一套风险口径

输入框可附带皮肤照片。图片**不依赖任何云 VLM**：本机 canvas 做像素统计（归一化泛红占比 `(r-g)/r ≥ 0.38` 计为偏红像素），转成结构化观察（无泛红 / 轻度 / 中度 / 明显）后命中「影像可见皮肤异常」信号，**按 policy.js 里与文本信号同一张权重表**叠加进风险分（+18），等级重算、处置建议同步更新。

`statsFromPixels` / `observe` 是纯函数（Node 与浏览器同结论），`analyzeFile` / `synth` 只在浏览器可用，并预留 `Vision.register()` 槽位 —— 接真 VLM 时注册即可，风险判定侧一行不改。

### 8.2 主动关怀雷达：出事之前先说话

风险引擎解决「出事之后怎么接住」，关怀雷达解决「出事之前能不能先开口」。三路信号全部从既有数据推算，不加埋点：

| 信号 | 推算逻辑 | 示例产出 |
|------|---------|---------|
| ① 复购周期 | 最近一单签收日 + 商品标定用量周期（PIM 兜底表）→ 用量进度 | 安瓶 7 支装超期 43 天 → 高危「复购超期」 |
| ② 权益挽留 | 保级消费线缺口 / 会员周年窗口 / 退换截止倒计时 | 钻石卡年度缺口 ¥4,340 → 高危「保级告急」 |
| ③ 成分冲突 | 肤质档案 × 商品成分（**订单联查优先，PIM 兜底**）+ 成分 × 成分叠加禁忌 | 购物车视黄醇 × 敏感肌 → 高危「加购成分禁忌」 |

每条建议都带数据出处（订单号 / 成分来源 / 口径声明）与可直接发送的话术草稿；有既往过敏史或未闭环工单的客户，销售类建议自动附加「服务优先」提示。基准日可用 `?today=2026-10-14` 固定，演示结论可复现。

### 8.3 会话复盘与交接摘要

工作台「复盘」把整个会话折叠成一张交接卡（数据全部来自逐轮判定记录，不重放推理）：

- **来意演进与情绪走势**（`物流催发 → 过敏投诉 · 情绪 57→48 明显转差`）；
- **承诺追踪** —— 坐席回复里出现「登记 / 跟进 / 补发 / 回电」等承诺词即记一笔，交接时先兑现；
- **未闭环事项** —— 顾客最后一条未回复、高危事件未接管、话术被合规拦截未补位、影像观察无后续，每条都指向可执行的下一步；
- **纯文本交接摘要**一键复制，直接粘进交接班文档。

### 8.4 隐私合规与审计导出

设置抽屉「隐私与审计」：一键把消息审计日志 + 风险事件 + 总线统计导出为 JSON。导出前按**确定性正则**脱敏（手机号 `138****10`、邮箱、证件号、订单号 `TM2026****137`、客户姓名），图片只记 `hasImage` 布尔值不导出本体；被总线拦截的消息本就不入册。脱敏规则被测试固定，结果幂等可复现。

### 8.5 多渠道接入与跨渠道用户合并

消费者的声音散在淘宝、天猫、京东、拼多多、抖音、小红书、微信、官网八个地方 —— 只接一个渠道，就只听得见一个渠道的人在说什么。

**① 接入不是点一下就冒出来，而是一步步跟你要东西。** 八个渠道登记成目录，每个渠道声明接入方式（开放平台 API / 插件嵌入 / Webhook 回推）、来源、能力边界（能不能拿到消息 / 订单 / 物流 / 售后 / 会员 / 内容），以及一份**接入要求**（平台侧前置条件、凭证字段与格式规则、回调约束、OAuth 授权范围、token 有效期、调用配额、签名方式）。接入走**六步向导**：

```
前置条件 → 接入凭证 → 连通性校验 → 店铺授权 → 数据冷启动 → 接入完成
```

- **前置条件**：逐条勾选（企业店铺 / 开发者实名 / 应用类目审核 / 权限包获批 / 服务器已备案…），未勾完不放行；
- **接入凭证**：按平台各自规则**本地校验** —— 淘宝 AppKey 8 位 + AppSecret + 店铺昵称 + 回调地址；京东 AppKey 16 位；拼多多 client_id 32 位十六进制；抖店 App Key 19 位；微信客服 corpId（`ww` + 16 位）+ Secret + Token（≤32 位）+ EncodingAESKey（**恰好 43 位**）。密钥打码显示、不明文回显，只出掩码指纹；
- **回调地址**：强制 HTTPS、公网可达；拒绝 `localhost` / `127.0.0.1` / 内网段，也**拒绝平台自家域名**（淘宝文档明确不许用淘宝域名做回调）；
- **连通性校验**：不假装成功。演示凭证会**真的探测失败**并回平台真实错误码（`code:15 Invalid app key`）；回调不通会回 `HTTP 404` —— 这正是真实接入最常见的卡点；
- **店铺授权**：跳 OAuth 地址，把浏览器地址栏里**完整**的回调地址粘回来；没有 `state` 直接拒绝（CSRF），`state` 被篡改也拒绝；授权码**一次性**、约 10 分钟过期；
- **数据冷启动**：按渠道拉历史会话逐条冷启动，**最后**才写入已接入列表 —— 前面任何一步没过都进不来。

**② 默认状态是「0 个已接入」—— 不预置任何假授权。** 打开渠道页看到的是八个都没接，指标「已接入 0 / 8 · 累计 0 条跨渠道消息」，合并用户 / 信息断层都是 0，跨渠道合并区为空并说明原因。这是刻意的：**没真的接过，就不该显示接过**。要看接入效果时用右上角「载入演示数据」、深链 `?demo=1` 或 `npm run demo:channels -- --demo`，页面顶部会挂橙色横幅声明「当前展示的是演示数据」。口径一致性是硬约束：**指标与列表必须同进同退**（单测与浏览器检查都有断言）。

**③ token 会过期，过期了消息就断。** 生命周期做成一等概念：`ok` / `soon`（≤3 天，卡片直接给续期入口）/ `expired` / `longterm`；续期方式按平台区分 `refresh_token`（淘宝 / 京东 / 拼多多 / 抖店 / 小红书）、`gettoken`（微信客服每 2 小时重新获取）、`none`（自有渠道）。演示数据里京东是**故意坏掉的**：access_token 只有 24 小时且无人续期 → 目录挂出「授权健康度：1 个已中断」，卡片描红、当日消息归零；它的 `refresh_token` 也已失效，**只能重新走一遍店铺授权**。

**④ 跨渠道用户合并 —— 这是「数据共情者」的地基。** 同一个消费者在不同渠道的痕迹按手机号 / 订单号 / 会员号归并成一个身份（演示态）：

```
周雨桐  139****8802 · JD2026092611884        2 个渠道 · 3 条痕迹 · 1 处断层
  京  09-26 12:08  订单  下单紧致抗老精华 30ml
  红  10-14 22:31  评论  在品牌笔记下留言「我要发小红书」   ← 本渠道看不到
  京  10-14 22:48  售后  反馈泛红并索要说法
```

一个人在天猫问成分、在小红书发空瓶记、回到天猫报不良反应 —— **三块碎片拼起来，AI 才真的懂她在意什么**。`gaps` 把「本渠道看不到的其他渠道信息」数出来，并区分**断层**（渠道已接入却看不到）与**盲区**（渠道压根没接）。

### 8.6 桌宠：手上那件道具从哪来

`propfit.js` 是品类判定的唯一真源：10 个品类映射到 7 个道具（**道具是包材形态的替身** —— 面霜共用圆罐、洁面共用软管、套装共用扁盒，形状承担不了品类名，名字交给气泡那行文字）。

- `classify()` 长词优先（「眼影盘」不能判成「眼影」），同长按词表顺序；
- `resolve({ messages, orders })` 优先级是**本会话最近一句原话 > 订单** —— 只认订单拿不到临时提到的品类，只认原话则一句「帮我退款」就空手；纯售后 / 情绪话术必须返回 `null`；
- 单测钉两件静默故障：词表里的道具**必须六态序列帧文件齐全**（hold / prun / pin / pnod / pwave / pspin）；无商品线索必须 `null`。

### 8.7 数据不再只放在网页里

账号、会话、自建话术落到服务端 `server/data/db.json`（`fs.renameSync` 原子替换），已 gitignore。口令只存 `sha256(salt:pin)`，令牌 24 字节 hex、TTL 12 小时。**服务端不可用时自动回落本机 localStorage**，界面提示「服务端不可用 · 先存本机」，不会静默丢数据。

### 9.3 全站优化审计：把「哪里慢、哪里废、哪里不合规」变成数字

`npm run audit`（`tools/audit.js`，零依赖，CDP 驱动真实 Chrome）—— 六段互相独立的测量，跑完把聚合结论打在终端，明细落 `%TEMP%\cs-audit\report.json`。支持 `--only=perf|a11y|churn|interact|css`、`--out=DIR`。

| 维度 | 怎么测 | 结果 |
|---|---|---|
| 可访问性 | 自写对比度检查：解析 `rgb()` → alpha 沿祖先链合成**真实绘制背景** → WCAG 相对亮度算比值；外加可访问名 / 表单标签 / `img alt` / 标题层级 / 重复 id / 对话框语义 | 12 个「视图 × 主题」组合的**对比度失败 31 → 0**；仅剩 1 条 `info`（4 个 `aria-live` 区域，属预期） |
| 性能 | `Performance.getMetrics` + `PerformanceObserver(longtask)` + 视图切换同步耗时 | 各视图 660–911 节点、深 9–11；切换不触发 layout |
| 渲染 churn | `MutationObserver` 统计「一次追加消息到底重建了多少节点」 | 最坏一次替换 **13 → 1** 个节点；疑似全量重建批次 **6 → 0** |
| 拖拽成本 | 180 次 `pointermove` 实测 | 32.3ms（**0.179ms / 次**）—— 便宜到不值得引入 rAF 批处理，属于**有数据支撑的「不改」** |
| 定时器 / 监听器泄漏 | 反复切视图 33 轮，每次回到同一视图再计数 | 增长 **0 节点**、堆 **−0.1MB** |
| CSS 死代码 | `CSS.startRuleUsageTracking` 跨全部视图 × 深浅两主题取并集 | 92.1KB 中未命中 **52.1KB（56.5%）** —— 如实记录，**未做删除**（含大量动态类名分支，盲删风险大于收益） |

三条方法论上的坑（都已写进代码注释）：

1. **CSS 覆盖率必须在 `reload` 之后取样式表文本** —— `Page.reload` 会让样式表拿到新的 `styleSheetId`；先取文本再 reload，usage 里的新 id 对不上旧文本，未使用率会恒等于 100%（看起来像「整个样式表都是死代码」）；
2. **浅色主题必须和深色一样被审计** —— 只测默认态会漏掉另一套配色，而实测**浅色才是重灾区**（工作台 43 项 vs 深色 25 项）。为此加了 `?theme=dark|light` 深链，默认浅色（客服台长时间盯屏，浅底更接近真实坐席后台）；
3. **泄漏探针必须先预热全部视图** —— 视图内容是首次进入才铺的（懒构建），不预热就取基线，量到的「增长」其实是「还有几屏没建过」，这个假阳性一度报出 +646 节点。

**配色为什么拆 `--accent` 与 `--accent-solid`**：一个色值不可能同时「够亮到能当文字」和「够暗到能托住白字」。原来 `--accent: #e0715c` 既当文字又当实心填充底色，配白字只有 **3.14**。现在拆成两个令牌（文字/描边/浅底 与 实心+白字），`--danger` / `--warn` / `--ok` 同理。**31 项不达标没有逐个元素改，而是收敛到 6 个调色板令牌求解** —— 固定色相饱和度、只降明度，步进到「所有真实背景上最小值 ≥ 4.7」为止（留 0.2 余量，避免四舍五入后卡在 4.49）。

### 10.1 一个单测碰不到的时序缺陷：坐席「抢跑」

**现象**：顾客消息到了、AI 还在读，坐席先手工回了一句。此后会话**永久停在那两条** —— 分析照常收尾、话术照常生成、界面一切正常，就是下一条顾客消息再也不会来。

**成因**：`deliverWhenIdle()` 是剧本推进的唯一闸门，只看 `S.awaitingReply`；标记为真就 `return` 且不重试。坐席 `sendAgent()` 把它置 `false` 并预约一次推进；但 `analyzeOne()` 是异步的，收尾时**无条件**执行 `S.awaitingReply = result.replies.length > 0`，晚于坐席那次回复执行 → 把「已经答过」写回「顾客还在等」。预约的推进随后看到标记为真 → 直接返回 → 剧本再无下文。这不是抖动，是**确定性**的。

**修法两条，一条治因一条兜底**：

1. 会话新增单调递增的 `replySeq`（坐席每发一条 +1），入队时把当时的 `replySeq` 冻结进 job；收尾改成 `S.awaitingReply = replies.length > 0 && S.replySeq === job.replySeq` —— 「这句消息到达**之后**才发出的回复」不算答复；
2. `deliverWhenIdle()` 不再单信这个会被异步回写的标记，改以**会话尾部**（`lastTurnIsCustomer()`）为准：尾部是坐席 = 已答，继续推进并就地校正标记。

**承重性验证**：把修复临时撤回基线，探针 **0/3 通过**；恢复后 **6/6 通过**（每轮都真抓到窗口，约 810ms 内续上）。通则：**跨异步边界的判断一律用「入队时冻结的依据」，并在收尾时用会话事实校正标记。**

### 10.2 三条只有端到端能守的护栏

这三类退化肉眼看不见（鼠标用户毫无感觉），只有按键 / 引用断言能守住：

- **`shell-a11y-focus`** —— 三个浮层都要拦 Tab（首尾环绕）、Esc 可关闭、并把焦点**归还给触发按钮**。接入向导此前压根不在 Esc 链里；向导每次重绘还会把焦点顶掉，现在按 `data-f` / `data-wz` / `data-ack` 记住焦点「身份」再还原。
- **`workbench-incremental-render`** —— 会话流曾整块 `innerHTML` 重建：每来一条消息就把全部气泡（含 dataURL 图片）重新解析解码一遍。用「**旧节点的引用必须还在**」来守，因为整块重建必然换掉引用；同时断言打字指示器**始终排在最后一条消息之后**。
- **`workbench-scroll-stick`** —— 坐席正在往上翻历史时被硬拽回底部。两条策略都要守：翻历史时不跟随、本就在底部时跟随。

> 这三条探针的**第一版全是假绿 / 假红**：① 工作台默认是坐席回复模式，直接 `btnSend` 只会追加一条客服消息，得靠剧本自己往下走才间接触发分析 —— 探针必须显式切到「模拟顾客」；② 测滚动策略时内容只溢出 40px，距底部仅 40px 还在 96px 的「贴底」阈值内，策略判定「跟随」**反而是对的** —— 那测的是阈值边界，不是策略。所以现在要求溢出余量 ≥ 240px。

## 十一、常见问题

**Q：点「测试连通性」报「返回内容为空」？**
请求已经打通（HTTP 200），只是没拿到正文。最常见原因是**模型是推理型的**（`deepseek-reasoner`、部分 thinking 变体），先输出推理内容把 token 配额吃光。系统已内置自愈：检测到会自动**提高 `max_tokens` 并去掉 `response_format` 重试一次**。仍失败就把模型名换成 `deepseek-chat`。

**Q：报 `HTTP 400 · Model Not Exist`？**
模型名写错了。DeepSeek 用 `deepseek-chat`（通用）或 `deepseek-reasoner`（推理）。错误信息会**原样透出上游原因**，不再是含糊的「调用失败」。

**Q：接口地址要带 `/v1` 吗？**
不用纠结。`https://api.deepseek.com`、`.../v1`、甚至整条 `.../v1/chat/completions` 都会被自动归一化；直连失败还会自动换另一种写法重试。

**Q：页面显示「已降级本地引擎」？**
鼠标悬停在右上角状态芯片上，**具体失败原因**会显示出来。常见原因：Key 未填 / 余额不足 / 模型名错误 / 浏览器直连被跨域拦截（改用 `npm start`）。

**Q：能换成其他模型吗？**
可以。接口地址兼容任何 OpenAI 协议端点（阿里云百炼、Moonshot、本地 Ollama）。支持 `response_format: {"type":"json_object"}` 的效果最佳，不支持会自动去掉该参数重试。

**Q：服务端日志显示「未配置」？**
正常。此时浏览器侧填的 Key 由代理透传；要让服务端代持，设 `DEEPSEEK_API_KEY` 后重启即可。

**Q：AI 只看最后一句吗？**
不是。每条消息进总线时都会**冻结一份前文快照**（最多 12 轮）一起送进模型，本轮无明确信号时回退到整段对话判意图。话术小助手顶部的「已读前文 N 句」和「查看前文」可直接核对。

**Q：刷新后账号和自建话术还在吗？**
在。它们落在服务端 `server/data/db.json`；服务端不可用时回落本机 localStorage 并提示。
